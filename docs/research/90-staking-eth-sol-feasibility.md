# ETH·SOL 스테이킹과 선물 헤지 — Phase 0 타당성 조사

작성: 2026-09-26 · 상태: **무료 이력 일부 확보 / 과거 수익 판정 전 / 데이터·안전성 설계 미완료**.

사용자 선택: ETH·SOL만 비교, 유료 데이터 구매 없음. 기존 전략·Paper·실계좌·스테이킹은 변경하지 않는다. 이 문서는 사전등록이나 실거래 승인이 아니다.

## 1. 이번 결론

- 비교 연구는 가능하다. 단순 보유에 대한 **스테이킹의 추가 기여**와, 가격 방향을 상쇄한 **스테이킹+선물 숏의 전체 자본 수익**을 분리한다.
- 업비트 SOL 표시 연 추정 보상률 **4.52%**는 2026-09-26 사용자가 전달한 현재 참고값이다. 계좌를 직접 조회하거나 지급 내역으로 검산한 값이 아니며, 과거 실현 수익률·미래 보장 수익률도 아니다.
- 업비트 표시 보상률은 서비스 수수료 차감 후 값이다. 4.52%에서 수수료 10%를 다시 빼지 않는다. 반대로 원시 네트워크 보상을 쓴다면 사업자 수수료 반영이 필요하다.[U1][U2]
- ETH의 업비트 실수령 보상률은 아직 미확인이다. Ethereum 웹 표시 APR 약 2.5%는 네트워크 참고값이지 업비트·Binance 상품 실수령률이 아니다.[E1] 이 수치로 ETH와 SOL의 우열을 판정하지 않는다.
- 기존 DB에는 ETH·SOL 현물/선물 가격과 펀딩 이력이 있지만 스테이킹 지급·환산비율 이력이 없고, 펀딩 행의 `mark_price`도 전부 비어 있다. 후속 감사에서 **Binance 상품 WBETH/BNSOL의 일별 환산비율, 공통 기간의 funding 정산 mark와 선물 mark 1시간봉**을 별도 연구 스냅숏으로 확보했다(§5.3~5.4). 이는 업비트 실제 보상이 아니며 틱별 청산 경로도 없으므로 비용 후 수익이나 청산 안전성 PASS/REJECT를 내리지 않는다.
- 신규 기여는 검증 보상이다. 선물 펀딩 수익 부분은 기존 K·M과 겹친다. **K·M 판정을 되돌리는 연구가 아니라, 보상을 더한 증가분이 추가 비용·위험에 합당한지** 검증한다.

## 3. 비교 구조와 수익원

연구군은 두 자산에 동일하게 적용한다. 자산별로 유리한 시점·조건을 탐색하지 않는다.

| 구분 | 목적 | 보유/청산과 비용 | 실패 가능성 |
|---|---|---|---|
| A: 단순 보유 기준선 | 같은 코인을 보유한 가격 수익 | 동일 평가 기간, 시작/종료 실현 비용 별도 | 코인 하락 |
| B: 스테이킹 단독 | A 대비 보상 증가분 | 신청·활성화·해제·환매 상태와 대기 반영 | 가격 하락, 수수료, 보상 감소, 출금 지연·사업자 위험 |
| C: 스테이킹+동일 코인 선물 숏 | 코인 방향을 대체로 상쇄한 보상+펀딩 | 보상으로 늘어난 수량에 헤지 조정 필요. 자금·보호주문·해제 규칙 확정 전 실행 금지 | 음수 펀딩, 숏 청산, 토큰 할인, 거래소 간 자금 분리 |

기존 **비스테이킹 현물+같은 선물 숏**을 C의 기여도 대조군으로 추가한다. 이는 새 전략 후보가 아니라 스테이킹 증가분을 식별하기 위한 회계 기준선이다. 기존 K·M 파라미터나 기각 판정을 수정하지 않는다.

진입 신호, 단기 가격 예측, RSI/펀딩 상위 자산 선정, 차입·재스테이킹·보상률 최적화는 이번 범위 밖이다. 자산 ETH·SOL만 고정하고 나머지 자유도(관측 기간·헤지 주기·자본 배분·stop·해제 규칙)는 수익 열람 전 별도 확정한다. 보유는 단기 매매가 아닌 지속 보유 후보이며 실제 평균 보유기간·거래 빈도는 아직 미정이다.

### 3.1 공정한 원장과 비교

- 전체 시작 자본 = 코인 평가액 + 선물 증거금 + 별도 비상자금. 기존 보유 코인도 시작 시점 시장가로 분모에 넣는다. 원가가 낮거나 이미 보유 중이라는 이유로 공짜 담보처럼 취급하지 않는다.
- 각 군에 동일 전체 자본을 주고 미투입 현금도 포함한다. 별도 표에서 동일 코인 수량 기준 증가분을 보여 준다. 두 표의 분모를 섞지 않는다.
- 스테이킹 보상은 실제 보상 수량과 지급/활성화 시각을 사용한다. APR/APY·복리 주기·수수료 중복을 구분하고 현재율을 과거 전체에 대입하지 않는다.
- 선물 funding 손익은 각 정산 시점 직전 보유 숏 수량 × 해당 정산 mark 가격 × 실제 funding rate. 실제 정산 간격을 쓰며 하루 3회로 고정하지 않는다. 양수는 숏 수취, 음수는 숏 지급이다.[B5]
- 전체 손익 = 스테이킹 자산 평가손익 + 선물 실현/미실현손익 + 순 funding + 현금 수익 − 비용. 보상이 이미 코인 수량/환산비율에 들어갔다면 다시 보상 현금을 더하지 않는다.
- 기준 통화는 USDT와 KRW를 각각 표시한다. 업비트 KRW 코인 평가와 Binance USDT 손익을 합칠 때 같은 시각의 환산율을 사용한다. 국내외 가격 프리미엄, USDT/USD 괴리와 환율 효과를 따로 분해한다. KRW 중립을 보장하지 않는다.
- 비용: 현물·선물 진입/청산, 스프레드·슬리피지, 헤지 조정, 스테이킹 수수료, 환매 할인, 실제 이체/환전 비용. 이미 보유한 업비트 SOL의 미래 증분 판단에는 과거 매수비용을 중복 부과하지 않되 신규 자본 대조군은 시작 비용을 반영한다.
- 세전 비교임을 명시하며 세후 수익은 세제·개인 요건을 별도 확인하기 전 주장하지 않는다.

### 3.2 SOL 4.52%로 보는 자본 분모 효과 — 예시, 백테스트 아님

보상률 4.52%가 1년 유지되고 가격·환율·괴리가 불변, 보상 평가 이외 비용/펀딩/현금 이자는 모두 0인 **단순 산술 가정**이다. 실제 APR/APY 방식은 지급 이력으로 다시 검산해야 한다. 표는 운용 배분 추천이나 위험 한도 예외가 아니다.

| 총자본 100 중 코인 / 현금 비중 | 코인 수량 기준 표시율 | 총자본 대비 스테이킹 기여 |
|---|---:|---:|
| 스테이킹 100 / 현금 0 (헤지 없음) | 4.52% | 4.52% — 가격 위험 그대로 |
| 스테이킹 2/3 / 현금 1/3 (헤지 가정) | 4.52% | 약 3.01% |
| 스테이킹 50 / 현금 50 (헤지 가정) | 4.52% | 2.26% |

마지막 행에 선물 명목 대비 1년 funding을 가정해 보면:

| 숏이 받는 funding / 선물 명목 | 총자본 대비 보상+funding 기여, 비용 전 |
|---|---:|
| −5% (숏이 지불) | −0.24% |
| 0% | 2.26% |
| +5% | 4.76% |

±5%는 **설명용 시나리오**, 과거 관측이나 전망이 아니다. 계산은 `0.5 × (4.52% + funding)`이며, 실제 funding은 기간 중 가격·수량 변화에 따라 달라진다. 단순 가정에서 손익분기 funding은 비용 전 −4.52%; 비용이 있으면 더 높아진다. '스테이킹 4.52% + 펀딩 5% = 계좌 9.52%'는 위 배분에서 잘못된 계산이다.

## 4. 업비트 SOL + 다른 거래소 숏의 핵심 위험

1. **상승 기회를 포기한다.** 완전 헤지는 SOL 급락뿐 아니라 SOL 급등의 이익도 대체로 상쇄한다. 사용자가 SOL 장기 상승을 원해서 보유했다면 다른 투자 목적이다. 지금 보유분에 헤지를 권하거나 실행하지 않는다.
2. **두 계좌의 돈은 자동 상계되지 않는다.** 단순 예로 SOL 평가액 100, 외부 현금 50, 같은 수량 숏에서 SOL이 50% 급등하면 숏 평가손실은 약 50이다. 현물 평가이익이 있어도 증거금 계좌에는 없으므로 유지증거금·비용 때문에 그 전에 청산될 수 있다. 이는 단순 스트레스 예시이지 실제 청산가 계산이 아니다.
3. **언스테이킹을 증거금 조달 계획으로 삼지 않는다.** 업비트의 예상 약 3일보다 더 걸릴 수 있고, 입출금 점검·이체 제한이 추가된다. 네트워크·거래소 상태와 적용 가능한 이체 요건을 확인해야 한다. 이번에는 송금·계정 변경 없음.
4. **숏 보호 stop이 체결되면 현물 롱만 남는다.** 스테이킹을 즉시 팔 수 없는 상태에서 노출이 바뀐다. 보호주문 필수 규칙을 끄거나 계속 무헤지로 버틴다는 가정을 넣지 않는다. 재헤지/해제/위험 축소를 포함한 두 계좌 상태 전이가 사전등록 전에 필요하다.
5. **기타 위험:** 음수 funding 장기화, ETH/SOL 보상 감소, 슬래싱/운영 페널티의 상품별 부담, 거래소·수탁·스마트계약 사고, WBETH/BNSOL 할인, KRW 프리미엄·환율 변화. 달러 기준 방향 상쇄가 모든 위험 제거는 아니다.

## 5. 실제 데이터 가용성 확인

### 5.1 로컬 읽기 전용 검사

검사 기준 코드: `400cd3c`. `data/trading.db`를 SQLite `mode=ro` + `PRAGMA query_only=ON`으로 읽었다. 데이터 적재·마이그레이션·삭제 없음. 금액/수익률 집계 없이 개수·범위·필드만 확인했다.

| 데이터 | ETHUSDT | SOLUSDT |
|---|---:|---:|
| `binance_usdm` funding 행 | 7,125 | 6,012 |
| funding 첫 기록(UTC 날짜) | 2020-03-01 | 2021-04-01 |
| funding 마지막 기록(UTC 날짜) | 2026-08-31 | 2026-08-31 |
| funding `mark_price` 채워진 행 | 0 | 0 |
| `binance_spot` 1h 봉 | 79,060 | 49,637 |
| `binance_usdm` 1h 봉 | 56,256 | 46,656 |

마지막 funding은 둘 다 2026-08-31 16:00:00.001 UTC. 전체 범위·행 수는 **완전성 통과가 아니다**. 간격 변경, 결측, 중복/시각 오차, 소스별 공통 구간 감사가 필요하다. 2026-09 자료는 위 DB 펀딩 조회에 없다.

`staking`/`reward`를 이름에 포함한 테이블이 없고, 조회한 1h/1d 봉에서 WBETHUSDT/BNSOLUSDT도 0행이다. 저장소 문서/코드 검색에서도 스테이킹 연구 경로는 발견하지 못했다. 외부 파일 전체 부재를 증명한 것은 아니다.

재현용 핵심 SQL:

```sql
SELECT symbol, COUNT(*), MIN(funding_ms), MAX(funding_ms),
       SUM(mark_price IS NOT NULL)
FROM funding_rates
WHERE exchange = 'binance_usdm' AND symbol IN ('ETHUSDT', 'SOLUSDT')
GROUP BY symbol;
```

### 5.2 공식 API 소량 접근 검사

2026-09-26, API 키·쿠키 없이 GET 6건. 응답의 값으로 수익률을 계산하지 않았다. 개인 API/계좌 접근·주문 없음.

| 경로 | 실제 결과 | 해석 |
|---|---|---|
| Binance `/fapi/v1/fundingRate?symbol=ETHUSDT&limit=1` | HTTP 200, 1행, `markPrice` 존재 | 공개 펀딩 경로 접근 가능. 과거 전체 mark 보존은 미검증 |
| 위 경로 SOLUSDT | 동일 | 동일 |
| Upbit `/v1/candles/days?market=KRW-ETH&count=1` | HTTP 200, 1행 | 공개 KRW 가격 경로 접근 가능 |
| 위 경로 KRW-SOL | 동일 | 동일 |
| Binance `/sapi/v1/eth-staking/eth/history/rateHistory` | HTTP 400, code −2014, API-key format invalid | 무서명 공개 API가 아님 |
| Binance `/sapi/v1/sol-staking/sol/history/rateHistory` | 동일 | 동일 |

공식 문서상 WBETH/BNSOL rate history는 서명된 `USER_DATA` GET이며, 1회 최대 3개월 범위/페이지 100건이다.[B3][B4] 유료 데이터 상품이라는 뜻은 아니나 키 없이 바로 수집할 수는 없다. 이번에는 기존 키를 읽거나 권한을 변경하지 않았다. API 문서 예시 APR/시각/환산비율을 관측값으로 사용하지 않는다.

펀딩 공개 응답에는 `fundingRate`, `fundingTime`, `markPrice`, `rateType`, `symbol`이 있었다. 실제 파서 작성 전 타입과 의미를 검증한다. 최근 한 점 조회로 과거 데이터 완전성을 주장하지 않는다.

업비트는 보상률 추이/보상 내역을 화면에서 제공한다고 안내한다.[U5] 이번 공식 자료 조사에서는 **장기간 업비트 상품별 실수령 보상 이력을 무인 수집할 공개 API 계약**을 확인하지 못했다. 사용자가 제공하는 내역은 로컬 비공개 자료로만 다루며, 네트워크 보상이나 Binance 비율을 업비트 실현값으로 대체하지 않는다.

### 5.3 무료 이력 수집·공통 기간 감사 (2026-09-26 후속)

`python -m scripts.audit_staking_rates`는 기존 Binance 읽기 전용 키로 서명된 **GET** rateHistory만 조회한다.[B3][B4] `python -m scripts.audit_staking_funding`은 공개 **GET** fundingRate와 로컬 DB를 읽기 전용으로 대조한다.[B6] 두 스크립트 모두 주문·계좌 보유량·개인 지급 내역을 조회하지 않는다. 정상화한 응답 행과 수집 시각·출처·SHA-256을 `data/research/staking/`에 저장한다. 이 경로는 Git 제외이며 운영 DB를 변경하지 않았다. API 원문 전체나 계좌 상태를 저장한 것은 아니다.

| 자료 | 기간(UTC, 양 끝 포함) | 행 수 | 날짜/대조 감사 |
|---|---|---:|---|
| Binance WBETH 환산비율 | 2023-04-24~2026-08-31 | 1,226일 | 시작 이후 일별 누락 0, 스냅숏 SHA 검증 |
| Binance BNSOL 환산비율 | 2024-08-28~2026-08-31 | 734일 | 시작 이후 일별 누락 0, 스냅숏 SHA 검증 |
| Binance ETHUSDT 정산 funding·mark | 2024-08-28~2026-08-31 | 2,202건 | 로컬 2,202건과 시각/비율 불일치 0, 공개 mark 결측 0 |
| Binance SOLUSDT 정산 funding·mark | 동일 | 2,202건 | 로컬 2,202건과 시각/비율 불일치 0, 공개 mark 결측 0 |

공동 비교에 사용할 수 있는 **자료의 겹침**은 2024-08-28~2026-08-31이다. 이것은 수익이 좋게 나온 기간을 고른 것이 아니라 BNSOL 이력의 첫 관측일과 2026-08 스냅숏 종료일의 교집합이다. 날짜 누락 0은 *관측 시작 후* 연속이라는 뜻이지 상품 출시 이후 완전성·보상 정확성을 보증하지 않는다. 두 상품의 과거 수수료·MEV·환산비율 적용/환매 가능 시점은 별도로 확인해야 한다. ETH·SOL 일별 관측을 독립 표본 수로 간주하지 않는다.

정산 시점 mark를 확보했고 §5.4에서 1시간 mark 고저도 수집했다. 그러나 **분·틱 단위 경로와 과거 유지증거금**, WBETH/BNSOL 매매가격·할인·환매 시점, 업비트 실제 SOL 지급 내역, KRW·USDT 환산/국내외 가격 차이 자료는 아직 없다. 이 상태로 크로스거래소 헤지·청산·총자본 손익을 계산하지 않는다. 업비트 SOL 4.52% 현재 표시율을 위 과거 구간에 대입하거나 BNSOL 비율로 업비트 수익을 대신하지 않는다. `DATA_INSUFFICIENT`와 전략 `REJECT`를 구별한다.

### 5.4 업비트 실지급 접근과 장중 mark 가용성 (2026-09-26 후속)

- [업비트 공식 안내][U5]는 로그인 후 **스테이킹 현황**에서 신청·해제·보상 내역을 확인하는 경로를 제시한다. 확인한 [공식 Open API 목록][U7]에는 스테이킹 보상 이력 조회 계약이 없다. 화면의 파일 내려받기 기능까지 확인한 것은 아니므로 CSV 내보내기를 단정하지 않는다. 계정 로그인·비공식 내부 API 호출·API 키 발급/권한 변경은 하지 않았다.
- 사용자가 원한다면 업비트 화면에서 **SOL 보상 지급 시각·지급 수량·MEV 여부, 스테이킹 활성화/해제 시각·수량**만 제공받아 로컬 비공개 자료로 대조할 수 있다. 이름·계좌번호·총 잔고·원가·거래내역·키/QR/인증정보는 제공할 필요가 없고 Git에 올리지 않는다. 현재 4.52% 표시율이나 누적보상 한 점은 과거 일별 실지급 시계열이 아니다. 사용자의 실제 스테이킹 시작 전 기간은 업비트 **실계좌 수익이 존재하지 않으므로**, Binance 2024~2026 이력과 동일한 과거 검증 표본으로 취급하지 않는다. 이 경우 업비트 비교는 향후 지급분을 누적하는 전향 관찰이다.
- [Binance 공개 mark 1시간봉 API][B7]를 `python -m scripts.audit_staking_mark_klines`로 **ETHUSDT·SOLUSDT 각 17,616봉**, 2024-08-28 00:00~2026-08-31 23:00 UTC에 수집했다. 기대 시간봉과 비교한 누락 0, 각 파일 SHA-256 재검산 일치. 정상화한 OHLC와 출처·수집시각·체크섬은 Git 제외 `data/research/staking/`에 있고 ETH 약 2.07 MB·SOL 약 1.99 MB다. 사용자 계좌나 운영 DB는 읽거나 바꾸지 않았다.
- **청산 판정은 여전히 불가.** 1시간봉 고저는 한 시간 내 시각·순서·틱 경로를 알 수 없다. 실제 숏 청산에는 포지션 수량·진입가·격리 증거금·펀딩 차감·유지증거금 tier/maintenance amount·보호주문/체결이 필요하다.[B8] [현재 notional/leverage bracket API][B9]는 사용자별 서명 조회이며 **과거 tier 이력 조회 계약이 아니다**. 현행 tier를 2024년부터 소급 적용하거나 단순 `1/레버리지`를 청산가로 쓰지 않는다. mark 봉은 가능한 스트레스 경로를 설계할 자료이지 안전 통과 증거가 아니다.

## 6. 다음 구현·검증 계획과 중단 기준

1. **Phase 0 데이터 감사:** §5.3~5.4의 Binance 환산비율·정산 mark·1시간 mark 수집과 업비트 공식 보상 내역 경로 확인은 완료했다. 다음에는 상품별 비율의 공개시각·수수료·MEV 포함 여부, 사용자 제공 시 업비트 실지급의 안전한 대조, 환매/할인, 더 세밀한 mark·과거 증거금 조건, KRW/USDT/프리미엄을 확인한다. 무상 자료로 검증할 수 없으면 `DATA_INSUFFICIENT`, 전략 기각과 구분한다. 키 권한을 거래/출금으로 올리지 않는다.
2. **보관 계약:** 현재 정상화된 응답 행과 소스/수집시각/기간/체크섬을 Git 제외 연구 디렉터리에 보존한다. API 원문 전체 보존은 아직 구현하지 않았으며 후속 자료에는 별도 계약이 필요하다. 개인 지급 내역·계좌 식별자·API 시크릿은 Git 제외. 현행 시장 DB/스케줄에 자동 수집을 추가하지 않는다.
3. **성과 열람 전 사전등록 준비:** 공통 자료 기간, 세전 통화, 동일 자본, 자금 배분, 헤지 시각·수량 내림, 청산/보호 stop 이후 행동, 환매 지연·수수료, 비용 2배 검사, 미열람 전향 구간을 고정한다. 기존 전략 수치를 복사해 신규 한도로 쓰지 않는다.
4. **검정력:** 일/epoch 보상을 독립 거래로 세지 않는다. 같은 시장에 노출된 ETH·SOL도 독립 표본 2배로 취급하지 않는다. 자기상관을 고려한 기간 블록의 계좌 순수익·대조군 대비 증가분으로 유효 표본/SE를 추정하고 80% 게이트를 확인한다. Binance 상품의 공통 가격/비율 구간은 확보했지만 **SD·업비트 실보상·완전한 헤지 원장 미확보**로 미계산/미통과다. 장기 캐리에 Phase 4 실제 거래 n≥100 기준을 어떻게 적용할지 사전 결정이 필요하며 임의 면제하지 않는다.
5. **이후에만 구현:** Pure Core 계산과 외부 자료 읽기를 분리하고 기존 연구 회계 구조를 재사용한다. Decimal 금액/수량, UTC ms, 실제 정산 시각, 양쪽 지갑 분리. 보상 누적·수수료 중복 방지·음수 funding·헤지 변화·급등 청산·환매 지연·stop 이후 잔여 롱·미래 무관성·결정론을 테스트한다. 기존 T/v2·O/v2 코드/설정 변경 없이 독립 연구 경로로 둔다.

경제성 판단은 전체 자본 기준 비용 후 수익과 위험, 동일 비스테이킹 캐리 대비 증가분으로 한다. 최소 요구수익·낙폭·자금잠김 허용치와 통계 판정은 결과를 보기 전 사용자와 확정한다. 자료가 충분해도 보호주문/위험 한도와 구조가 충돌하거나 스트레스에서 청산 위험을 감당할 수 없으면 실행 후보로 승격하지 않는다. 펀딩이 음수여도 보상을 무조건 확보한다고 가정하거나, 수익률이 낮다는 이유로 레버리지를 올려 통과시키지 않는다.
