## 4. 실행 안전성 감사

### 확인된 기반

- 일반 매매는 `submit_capped`: mark ±0.3% 지정가 IOC, 최대 3회, 결과 미상에서는 재주문 중단.
- 불명 주문/재시작 대조, reduce-only 축소, 다리 스톱 교체, 보호 실패 비상 정리의 기존 FakeExchange 시험이 있다.
- 데모는 별도 `demo_o2.db`. 다른 전략의 미해결 주문까지 보는 `blocked()`의 C10 경계를 공유 DB로 우회하지 않는다.
- 실계좌 `BinanceUsdmReadOnly`의 주문/취소는 차단 상태다. 이를 해제하지 않았다.

### F1 — 데모와 전체 위험 규칙의 차이(기존에 명시된 제한)

`demo_o2_futures.py`는 `increases_allowed=True`를 전달한다.
실행기의 `daily_loss_blocks_increase` 함수는 있으나 호출자의 UTC 일 시작 equity·통합 DD 상태가 연결되지 않았다.
가상 O/v2의 일 손실 2%·계좌 정지 30%를 데모가 완전히 재현하지 않는다는 것은 문서 59에 이미 명시돼 있다.
현물 평가액을 기준으로 ETH 추가분을 따로 거래하고 지갑 이체·통합 레버리지/청산거리 가드는 완성 경로가 아니다.
따라서 데모 `OK`를 전체 위험 규칙 통과로 바꾸면 안 된다.

### F2 — 보호 공백 5초: 합성 반례 확인 / 미수정

규정: 첫 체결부터 보호 공백 5,000ms 초과 시 비상 정리·HALTED.

실제 운영 DB 대신 **메모리 SQLite + FakeFuturesExchange + 주입 시계**로 재현했다.

1. BTCUSDT 0.1 지정가 IOC 롱 체결을 가짜 시각 0ms에 수락.
2. 주문의 체결 응답이 호출자에게 돌아오기 전 주입 시계를 6,000ms 앞으로 이동(응답 지연 모사, 실제 sleep/네트워크 없음).
3. 기존 `OverlayFuturesExecutor.run`을 그대로 진행해 최초 보호 스톱이 6,000ms에 수락됨.
4. 결과: 보호 공백 **6,000ms**, 최종 포지션 0.1·보호 스톱 1개, 실행 상태 **OK**, 비상 정리 주문 0, 경고 0.

원인 경로: `_trade → submit_capped`가 반환된 다음 `_maintain_stop`을 호출한다.
`_protect_or_close`의 3초 창은 보호 재시도 시작부터의 창이지 첫 체결부터 5초를 세는 창이 아니다.
최종 스톱 존재 확인만으로 앞선 보호 공백 위반이 사라진다. 신규 진입뿐 아니라 부분 체결/응답 미상/다중 IOC에서 같은 경계를 검증해야 한다.

이것은 **실거래 사고가 아닌 합성 진단**이다. 기존 수익 판정은 바꾸지 않는다.
현재 정상 입력 시험이 통과하더라도 지연 안전성의 이 반례가 해결됐다는 뜻이 아니다.
코드 변경 없이 [Current 미해결 C11](../current/CURRENT_SPEC.md)에 등록했다.

## 5. 후속 작업 — 적용 전에 필요한 검증

우선순위는 다음과 같다. 이번 감사가 구현·데모 재주문·실거래 활성화를 승인하는 것은 아니다.

1. **Phase 5 실행 안전성 보완:** F2를 지속 회귀 시험으로 고정. 첫 부분 체결부터 보호 확인까지의 시간 기록, 지연/UNKNOWN 시 독립 감시, 5초 경계·6초 초과·프로세스 종료/복구 시험. 위험 한도를 넓히거나 시작 시점을 보호 재시도로 옮겨 통과시키지 않는다.
2. **Phase 5 비용 원장 설계:** 기존 `userTrades` 조회를 활용해 실제 fee/fee_asset·체결 명목, funding 정산·mark·포지션을 기록/대조. 결측은 0이 아닌 미확인. 주문 생성과 분리하고 가격/수수료/미체결 비용을 나눠 보고한다.
3. **Phase 5 통합 위험 연결 검토:** UTC 시작 equity·고점/DD의 영속 복구, 일 손실 증가 차단·청산 허용, 선물 지갑 잔고·이체 멱등성·청산거리 가드. 교차/격리와 전략 한정 위험 예외는 문서 50의 별도 사용자 승인 대상이다.
4. **Phase 7 실행 검증:** 위 회귀가 통과하고 별도 실행 승인을 받은 뒤 데모에서 지정가 신규 진입/부분 체결·보호 지연·WS 단절·재시작을 확인. 기존 전략 종목 배분과 훈련 종료 판정을 먼저 확인; 날짜가 지났다는 이유만으로 BTC를 추가하지 않는다.
5. **Phase 6 관찰 지속:** 10/23·10/24 기존 점검 계약 유지. 15일 성과로 배수·스톱·종목·시간대를 고르거나 12개월 계약을 축소하지 않는다.

### 시간 의미와 동작

- 실제 첫 체결 시각을 현재 주문 인터페이스에서 얻지 못한다. 보호가 부족한 증가 주문의 전송 **전**
  시작 시각을 SQLite에 선기록하고, 이후 보호 확인까지를 **보수적인 잠재 무보호 시간 상한**으로 센다.
  정확한 거래소 체결→스톱 수락 공백의 실측은 아니다. 보호가 일찍 수락됐어도 확인 응답이 늦으면 정지할 수 있다.
- 각 IOC의 응답 뒤 계좌를 조회하고 부분체결에 보호를 등록·거래소 조회로 확인한 다음에만 다음 IOC를 보낸다.
  기존 closePosition이 증가 후 전체 수량을 보호한다면 느린 증가 응답 자체를 무보호 위반으로 세지 않는다.
- 시작~확인 상한 5,000ms는 허용, 5,001ms 이상/시계 역행은 HALTED. 확인된 롱 포지션만
  보호 공백 예외 reduce-only 비상 시장가 정리한다. 포지션 미확인 때 추정 주문은 보내지 않는다.
  늦은 응답이라도 실제 미체결·포지션 0·미확정 주문 없음이면 가짜 포지션/청산을 만들지 않는다.
- 미확정 CLOSE는 새 ID로 추정 재청산하지 않고 대조를 계속한다. 청산 후 계좌 조회가 실패하면
  완료로 기록하지 않는다. 정지 상태에서도 확인된 수량 축소와 보호 등록은 허용한다.
- 기존 `risk_events`에 `PROTECTION_STARTED/FINISHED/HALTED`를 mode·strategy_tag·symbol로 기록한다.
  Overlay 실행기의 보호 정지는 날짜/프로세스 재시작으로 자동 해제하지 않으며, 오래된 정지가
  최근 500행 밖으로 밀려 없어지지 않도록 범위별 마지막 기록을 읽는다. 사람 승인 없는 자동 리셋은 없다.
  다른 실행기 전체의 통합 HALTED 연결을 완료했다는 의미는 아니다.
- 데모 저장 보고에 `protection_elapsed_upper_ms`를 추가한다. 기존 일반 주문의 지정가/가격 상한/횟수는 유지한다.

### 아직 해결하지 못한 경계

**동기 HTTP가 반환되지 않는 동안에는 이 코드가 별도로 작동할 수 없다.** 이 보완은 API 반환/조회 후
위반을 감지하는 것이지 5초 내 실제 보호/청산을 보장하는 watchdog이 아니다. 프로세스가 죽어도 DB의
시작 시각은 보존되지만, 다시 켜기 전 청산을 실행하지는 못한다. 따라서 Current C11은 **부분 보완·미해결**이다.

다음 별도 Phase 5 범위는 독립 감시 주체·주문 소유권/멱등성·동시 청산 경합 방지·API 시간 제한·
실제 첫 체결 시각 확보·프로세스 강제 종료/복구 시험이다. 공유 DB C10·미확정 주문·수동/외부 주문과
충돌하지 않도록 설계를 먼저 확정한다. 이 작업 없이 실거래 준비 완료로 부르지 않는다.

후속 감시 설계에서 특히 고정할 계약:

1. 주 실행기와 감시기는 같은 체결/보호 세대를 보고, 주문 전 기록을 먼저 공유한다.
   UTC 영속 시각과 실행 중 단조 시계의 역할을 분리하고 시계 역행/조회 결측은 정상으로 숨기지 않는다.
2. 위험 축소 주문의 소유권·세대·멱등 ID를 하나로 정한다. 주 실행기의 늦은 응답과 감시기의
   청산이 겹쳐도 별개 ID로 중복 청산하지 않으며, UNKNOWN은 조회로만 해소한다.
   SQLite 연결은 실행 주체별로 분리하고, 원자적인 소유권 획득/갱신을 시험한다.
3. 주문 POST·계좌/스톱 조회별 지연, 주 실행기 종료, 감시기 종료, 재시작,
   네트워크 전체 단절·부분 체결·청산 응답 유실·늦은 스톱 수락을 주입한다.
   거래소가 응답 불능이면 독립 감시도 5초 내 체결을 보장할 수 없다는 한계를 명시하고,
   실제 초과 시간·추가 노출 차단·보호/청산 미확인·경고를 거짓 완료 없이 기록한다.

이번에는 감시 프로세스/예약을 추가하거나 기존 데모를 직접 실행하지 않았다. 수정한 실행기 코드는
다음 정규 데모 프로세스가 파일을 새로 읽을 때 사용될 수 있으나, 전략·예약·실거래 권한은 그대로다.
