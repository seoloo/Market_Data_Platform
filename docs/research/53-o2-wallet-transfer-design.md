# 53 — O/v2 안전성 검증 V3: 현물 ↔ 선물 지갑 이체 설계와 하루 실행 순서 (2026-09-25)

작성: 2026-09-25 (Claude) · 상태: **설계 + 순수 계획기·이체 관리자·가짜 지갑 시험 완료.**
- 실계좌 이체는 하지 않았고, 그 구현도 만들지 않았다. 자금 이동이라 Phase 8 2단계 승인 뒤에 한다.
- 운영 중인 Paper·전략은 바꾸지 않았다.

사용자 요청: "V3 진행해줘" ([52](52-o2-continuation-safety.md) §3).

## 1. 왜 이체가 필요한가

O 는 현물에 `k·w`, 선물에 `(1.5 − k)·w` 를 두고, **현물 밖 자본은 전부 선물 지갑(교차 증거금)** 에 둔다(24 §2).
Binance 에서 현물 지갑과 USD-M 선물 지갑은 따로다. 그래서 목표가 바뀌는 날에는 돈을 옮겨야 한다.
- 현물을 더 사려면 선물 지갑의 USDT 를 현물로 옮긴다.
- 현물을 판 돈은 선물 지갑으로 보낸다.

**실제로 이체가 필요한 날은 대부분 작다.** T/v2 비중이 연 수십 번 바뀌고, 밴드(5%p) 안의 변화는 거래하지 않는다.

## 2. Binance 이체 API (공식 문서, 2026-09-25 확인)

| 항목 | 내용 |
|---|---|
| 이체 | `POST /sapi/v1/asset/transfer`. `type` = `MAIN_UMFUTURE`(현물→USD-M) · `UMFUTURE_MAIN`(USD-M→현물), `asset`, `amount`. 응답 `tranId` |
| 권한 | API 키에 **"Permits Universal Transfer"** 를 켜야 한다 |
| 이력 | `GET /sapi/v1/asset/transfer` (`type`, `startTime`, `endTime`, `size` ≤ 100). **최근 6개월만**, 기간이 없으면 최근 7일 |
| 멱등 | **클라이언트가 정하는 ID 항목이 없다.** 주문의 `newClientOrderId` 같은 것이 없어, 응답을 잃으면 이체가 됐는지 이력으로만 알 수 있다 |

출처:
- [User Universal Transfer](https://developers.binance.com/docs/wallet/asset/user-universal-transfer)
- [Query User Universal Transfer History](https://developers.binance.com/docs/wallet/asset/query-user-universal-transfer)

**보안 영향:** 이 권한은 **본인 지갑 사이 이동**이지 출금이 아니다. 그래도 권한이 늘어난다. 2단계 키는 다음 조건이어야 한다.
- 현물·선물 거래와 이 권한만 켠다
- **출금은 끈다**
- IP 제한을 둔다

키 권한을 켜는 것은 사용자가 한다. 그림자 운영(51)은 지금 이 권한이 **꺼져 있어야** 정상으로 본다.
Phase 8 1단계·2단계 승인 때 점검 기준을 바꾼다.

## 3. 이체 관리자 — 멱등 의도 · 선기록 · 이력 조회 해소

`execution/wallet_transfers.py` (`WalletTransferManager`), 기록은 `wallet_transfers` 테이블(마이그레이션 009).
주문 관리자와 같은 규약을 따르되, 멱등 ID 가 없어서 더 조심한다.

| 규칙 | 내용 |
|---|---|
| 의도 ID | 전략 태그·결정 시각·방향(+재발행 번호) — 예 `o2-<결정>-S2F`. 같은 의도는 몇 번 불러도 한 건 |
| 선기록 | 거래소 호출 **전에** PENDING 을 커밋한다 |
| 결과를 모름 (UNKNOWN) | **다시 보내지 않는다.** 이력(생성 2분 전 ~ 지금)에서 같은 방향·자산·금액이고 **다른 기록이 아직 가져가지 않은** tranId 를 찾는다 |
| 정확히 1건 | CONFIRMED (tranId 기록) |
| 여러 건 | UNKNOWN 유지 — "사람 확인". 예: 같은 시각에 사람이 같은 금액을 손으로 옮긴 경우 |
| 0건 | 10분이 지나기 전이면 UNKNOWN 유지(이력이 늦게 보일 수 있다). 지나면 NOT_FOUND 로 닫는다 |
| 재발행 | NOT_FOUND 뒤 다시 보내려면 `attempt` 를 올려 **새 의도를 명시**한다 |
| 막기 | 해소되지 않은 이체가 하나라도 있으면 **새 이체를 받지 않는다.** 그 돈에 기대는 주문(현물 매수·선물 늘리기)도 하지 않는다 |

## 4. 하루 실행 순서 — 계획기

`execution/overlay_plan.py` (`plan_overlay_day`)는 순수 함수다. 실행 직전 계좌와 목표 수량으로 순서와 금액을 정한다.

| 순서 | 단계 | 조건·금액 |
|---|---|---|
| 1 | **선물 줄이기** | 목표 < 현재. 증거금이 먼저 풀린다 |
| 2 | **현물 팔기** | 목표 < 현재 |
| 3 | **선물 → 현물 이체** | 현물 매수에 현금이 모자랄 때만. 모자란 만큼, 단 **선물 지갑 최소 금액**을 남긴다 |
| 4 | **현물 사기** | 이체가 모자라면 **매수를 비례해 줄인다**(기록) |
| 5 | **현물 → 선물 이체** | 남는 현금(예비 1 USDT 제외, 1 USDT 이상일 때) |
| 6 | **선물 늘리기** | 선물 명목 ≤ 3 × 선물 지갑. 넘으면 늘리기를 줄인다(O 규칙) |

**선물 지갑 최소 금액** = max(목표 선물 명목 / 3, 1.5 × 목표 선물 명목 / 거래소 레버리지 설정).
- 앞은 O 의 레버리지 상한이다.
- 뒤는 TRADING_CORE 의 "필요 증거금의 1.5배 가용 잔고"다.
- 거래소 레버리지를 **5배로 설정**하면 필요 증거금이 명목의 20%, 1.5배면 30% 라서 O 의 33% 가 더 크다. 두 규칙을 함께 지킨다.
- 레버리지 설정이 3배면 1.5배 규칙(명목의 50%)이 더 커진다(시험 있음).
- 레버리지 설정은 증거금 계산일 뿐이다. **실제 노출은 O 규칙(최대 3배)이 정한다.**

**단계 사이 의존 (실행기가 지킨다):**
- 3 의 이체가 **CONFIRMED** 여야 4(현물 매수)를 한다. UNKNOWN·REJECTED 면 매수를 건너뛴다.
  이미 한 1·2 는 위험을 줄이는 일이라 그대로 둔다.
- 5 의 이체가 CONFIRMED 여야 6(선물 늘리기)을 한다.
- 6 뒤에는 V2 실행기의 스톱 교체와 마지막 확인이 이어진다(52 §6).
- 긴급 정지 스위치·그날 손실 2%·복구 DEGRADED 면 4·6(늘리기)과 그에 필요한 3·5 이체를 하지 않는다. 1·2 와 보호는 계속한다.

## 5. 시험 (가짜 지갑·순수 계획기, 18건)

| 이체 관리자 (10건) | 결과 |
|---|---|
| 정상 이체를 두 번 호출 | 이체 1건, 같은 기록 |
| 잔고 부족 거부 | REJECTED, 돈 안 움직임, 막히지 않음 |
| 이체 뒤 응답 유실 | UNKNOWN → 새 이체 거부 → 복구가 이력에서 tranId 를 찾아 CONFIRMED. 이체 1건 |
| 보내기 전 네트워크 오류 | 10분 전 복구는 UNKNOWN 유지 → 뒤에는 NOT_FOUND → attempt=1 로 명시적 재이체 |
| 선기록 뒤 응답 기록 전에 꺼짐 | 복구가 이력에서 찾아 CONFIRMED |
| 같은 금액의 이전 이체가 있음 | 이미 가져간 tranId 는 다시 쓰지 않는다 |
| 사람이 같은 금액을 손으로 옮김 | 2건 일치 → UNKNOWN 유지 "사람 확인" |
| 이력 조회 실패 | UNKNOWN 유지 |
| 0.01 미만 금액 | 거부 |

| 계획기 (8건) | 결과 |
|---|---|
| 순서 | 줄이기 → 팔기 → 이체 → 사기 → 이체 → 늘리기 |
| 매수 현금 부족 | 선물 → 현물 이체 = 모자란 만큼 |
| 선물 지갑 최소 금액 | 이체를 그만큼만, 매수를 줄이고 기록 |
| 남는 현금 | 선물 지갑으로 (예비 1 USDT) |
| 선물 늘리기 | 지갑 3배에서 자름 |
| 거래소 레버리지 3배 설정 | 1.5배 규칙이 최소 금액을 정함 |
| 할 일 없음 | 단계 0 |
| **속성 시험** (hypothesis 150개 계좌·목표) | 순서 유지, 금액 양수, 선물→현물 이체 뒤 지갑 ≥ 최소 금액, 늘리기 뒤 명목 ≤ 지갑 3배 |

## 6. 한계와 남은 것

- **실계좌 이체 어댑터가 없다.** Phase 8 2단계 승인 뒤, 먼저 이체 **이력 읽기만**으로 응답 형식을 확인하고 나서 만든다.
  테스트넷(선물 데모)에는 현물 지갑이 없어서 이체를 거기서 시험할 수 없다.
- 이력의 금액 표기(소수 자리)와 시각이 우리 기록과 정확히 맞는지는 실계좌 첫 확인에서 본다.
- 현물 주문·이체·선물 실행기를 한 번에 묶는 **O 하루 실행기(오케스트레이터)** 는 아직 없다. V4(테스트넷 며칠)는 선물 다리만 돈다.
  묶음은 2단계 직전에 만든다(순서·의존은 §4 그대로).
- 서브 계정에 전략 자금을 따로 두면 개인 보유분과 섞이지 않아 대조가 쉽다. 계정 조건은 사용자가 확인해야 한다.
