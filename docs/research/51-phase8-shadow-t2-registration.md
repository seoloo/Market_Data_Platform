## 1. 무엇을 하고 무엇을 하지 않나

| 한다 | 하지 않는다 |
|---|---|
| Paper 와 **같은 실행기**를 **실거래 예정 금액**으로 매일 돌린다 (별도 원장 `t2_shadow_<금액>`, `spot_orders` mode='shadow') | **거래소에 주문을 보내지 않는다.** 실계좌 어댑터(`BinanceSpotReadOnly`)는 주문 요청을 항상 거부한다. Phase 8 승인 전에는 주문 경로가 없다 |
| 실계좌를 **읽기만** 한다: 키 권한, 서버 시계, 잔고 | 키 권한을 바꾸지 않는다. 거래 권한 키는 Phase 8 승인 뒤 사용자가 만든다 |
| 그날 주문 크기와 고정 크기(100·1,000·10,000 USDT)로 **호가를 읽어 미끄러짐을 추정**한다 | 지갑 이체·입금을 하지 않는다 |
| **긴급 정지 스위치** `data/HALT` 가 있으면 실거래처럼 그날 체결하지 않는다 | 정지 파일을 만들거나 지우지 않는다 (사람의 결정) |
| 목표 비중이 T/v2 Paper 와 같은지 매일 대조한다 (같은 신호·같은 코드) | Paper 원장을 건드리지 않는다 |

**Paper 와 다른 점:**
- 금액이 작다. 작은 금액에서만 드러나는 수량 단위·최소 주문 금액(5 USDT) 영향이 보인다.
- 실계좌 준비 상태와 실제 호가를 함께 본다.

## 2. 매일 점검 항목과 경고 수준

일일 점검(21:20 텔레그램)에 `그림자 운영: <날짜> <상태> · 예정 <금액> USDT · 가상 자본 …` 한 줄이 추가된다.

| 점검 | 수준 | 뜻 |
|---|---|---|
| 실계좌 키에 읽기 외 권한(현물 거래·출금·선물 등)이 켜짐 | **CRITICAL** | Phase 8 승인 전인데 키가 위험하다. 즉시 키를 확인한다 |
| 키에 IP 제한이 없음 | **CRITICAL** | 같음 |
| 보고서에 "거래소 주문 > 0" | **CRITICAL** | 있을 수 없는 일이다. 코드 결함으로 보고 멈춘다 |
| 실행 누락(하루 이상 밀림)·실행 실패 | WARN | PC 꺼짐·네트워크. Paper 와 같은 원칙으로 다음 실행이 새 목표만 정한다 |
| 긴급 정지 스위치 켜짐 | WARN | 켠 사람이 의도한 것인지 확인 |
| 목표와 실제 비중 차이 > 5%p, Paper 와 목표 불일치 | WARN | 최소 주문·수량 단위 영향 또는 코드 차이. 원인을 기록한다 |
| 서버 시계 차이 > 1초, 키·잔고 조회 실패 | WARN | 실거래였다면 주문 서명이 거부될 수 있다 |
| 실계좌 평가액 < 예정 금액 | INFO | 실거래 시작 전에 입금이 필요하다는 알림일 뿐이다 |

## 5. 긴급 정지 스위치와 장애 대응 절차 (Phase 8 에 그대로 쓴다)

### 5.1 긴급 정지

- **켜기:** 프로젝트의 `data` 폴더에 `HALT` 라는 파일을 만든다. 첫 줄에 사유를 쓴다(예: `거래소 점검 공지`). 메모장으로 충분하다.
- **효과:** 그림자 운영은 그날 체결하지 않고 WARN 을 남긴다. Phase 8 실행기도 같은 파일을 읽어 **신규 주문을 멈추게** 만든다.
  위험 축소(청산)는 막지 않는다는 원칙은 유지한다.
- **끄기:** 파일을 지운다. 다음 실행부터 정상이다. 정지 중 빠진 날의 목표는 체결하지 않는다(오래된 목표 금지 원칙).

### 5.2 알림별 대응

| 알림 | 할 일 |
|---|---|
| 키 권한 CRITICAL | Binance API 관리에서 해당 키의 권한과 IP 제한을 확인한다. 의도하지 않았으면 키를 삭제하고 읽기 전용 키를 다시 만든다 |
| 주문 > 0 CRITICAL | `data/HALT` 를 만들고 에이전트에게 알린다. 코드를 고치기 전까지 그림자 운영을 멈춘다 |
| 며칠째 실행 누락 | 작업 스케줄러 '마지막 결과'와 PC 절전 설정을 확인한다. 상시 가동 환경 검토(과제 3)의 근거로 기록한다 |
| 목표 불일치 | 보고서 `reports/shadow/t2/<날짜>.json` 의 `tracking_gaps` 를 에이전트에게 보여 준다 |

## 6. 운영 등록 (사용자가 1회 실행)

**등록 (2026-09-25):** 사용자가 `--allocation 10000` 으로 등록했다(원장 `t2_shadow_10000`). Paper 와 같은 금액이라 최소 주문 영향은 거의 드러나지 않고, 대신 실계좌·호가·Paper 대조 점검이 중심이 된다.

**먼저 정할 것: 실거래 예정 금액(USDT).** 원장은 금액별로 따로 쌓이므로, 나중에 금액을 바꾸면 새 원장으로 다시 시작한다.
`--allocation` 에 그 금액을 넣어 등록한다. 아래 예시는 1,000 USDT 다.

```powershell
Register-ScheduledTask -TaskName "AutoTrading_Shadow_T2" -Action (New-ScheduledTaskAction -Execute "C:\Users\seolh\Documents\GitHub\Auto_Trading\.venv\Scripts\python.exe" -Argument "C:\Users\seolh\Documents\GitHub\Auto_Trading\scripts\run_shadow_t2.py run --allocation 1000") -Trigger (New-ScheduledTaskTrigger -Daily -At 21:10)
```

순서: T/v2 21:00 → O 21:02~21:06 → 테스트넷 21:08 → **그림자 21:10** → 점검 21:20.
