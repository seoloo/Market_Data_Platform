# O/v2 독립 보호 감시 — 설계 초안

작성: 2026-10-09 · 상태: **DRAFT / NOT_IMPLEMENTED / NOT_TESTED**

사용자 "다음 작업"에 따른 Phase 5 C11 후속 설계다. 운영은 Phase 6 Paper 유지.
이번에는 문서만 작성하며 코드·DB·설정·예약·키 권한·거래소 주문을 변경하지 않는다.
설계 권고는 구현/데모 실행/실거래 활성화 승인이나 게이트 통과가 아니다.

기준: [TRADING_CORE](../current/TRADING_CORE.md), [검증 게이트](../current/BACKTEST_AND_TESTING.md),
[운영](../current/OPERATIONS.md), [직전 감사·부분 보완](O2_FUTURES_READINESS_AUDIT.md).

## 1. 목적과 보장 범위

현재 보완은 동기 API가 돌아온 뒤 보호 확인 지연을 감지한다. 다음 목표는 매매 계산 프로세스나
주문 HTTP가 멈추더라도 별도 안전 프로세스가 시간·주문 상태를 관찰하고 노출 증가를 막는 것이다.

- 일반 OPEN/REDUCE/CLOSE는 기존 가격 한도 지정가 유지. 보호 공백/등록 실패 비상 정리만
  승인된 시장가 예외를 사용한다. 손절 가격·배수·종목·수익 규칙·위험 한도는 변경하지 않는다.
- 첫 체결부터 보호 공백 **5,000ms 초과** 규칙과 보호 재시도 **3회/총 3초**는 별개이며 유지한다.
- 독립 프로세스도 같은 PC/전원/회선/거래소에 의존한다. PC 전체 정지·거래소 장애에는
  5초 내 보호/청산 체결을 보장할 수 없다. 이미 거래소에 등록된 스톱은 별도의 보호 수단이다.
- heartbeat 소실은 매매 프로그램 이상이지 보호 공백의 증거가 아니다. 정상 보호 중인 포지션을
  heartbeat만으로 시장가 정리하지 않는다. 신규 노출 차단·원격 보호 대조·경고를 먼저 한다.
- 수익률 개선 연구가 아니라 사고 방지 인프라다. 기존 연구 PASS/REJECT와 Paper 계약을 바꾸지 않는다.

## 2. 코드에서 확인한 연결 지점과 도입 전 관문

| 근거 | 확인한 사실 | 독립 감시 도입 전 처리 |
|---|---|---|
| `execution/overlay_futures.py` | IOC별 보호와 지연 발견 뒤 정지는 있으나 동기 API 중 별도 개입 없음 | 매매 계산과 안전 제어/HTTP 대기를 분리 |
| `execution/futures_guard.py`, `risk_events` | STARTED/FINISHED/HALTED 감사 기록은 있음 | 감사 로그를 원자적 주문 전송 권한으로 오인하지 않음 |
| `execution/futures_orders.py::_reconcile` | PENDING/UNKNOWN 원격 조회가 부재면 NOT_PLACED로 바꿈 | 다른 프로세스의 HTTP가 진행 중일 때 부재 응답만으로 부재 확정 금지 |
| `futures_orders.py::_new_record`, 저장소 `insert/update` | ID UNIQUE·선기록은 있음. 동시 요청자는 insert 충돌 가능, update는 버전 비교 없이 덮어씀 | 단일 전송 조정·claim·세대/CAS·역순 결과 방어 필요. UNIQUE만으로 다중 실행 안전성 완료 아님 |
| `exchange/binance_usdm.py` | 기본 `httpx.Client(timeout=10.0)` | 5초 전체 보호 시한과 동일한 타이머가 아님 |
| `storage/db.py` | 기본 busy_timeout 5,000ms, WAL + synchronous=NORMAL | 안전 루프에서 5초 DB 대기 금지, 핵심 기록의 정전 내구성 별도 검증 |
| `exchange/user_stream.py::OrderUpdate`, `execution/stream_sync.py` | trade_ms/event_ms 필드는 있으나 이벤트가 주로 원주문 REST 재조회로 이어짐 | 실제 첫 체결 시각의 영속 연결·중복/역순/재연결 계약 필요 |

HTTPX는 connect/read/write/pool별 timeout을 구분하고 read timeout은 응답 chunk를 기다리는 시간이다.
따라서 현재 10초 설정이나 이를 단순히 줄인 설정을 전체 작업 완료 기한으로 해석하면 안 된다.
[HTTPX 공식 설명](https://www.python-httpx.org/advanced/timeouts/).

SQLite WAL/NORMAL은 애플리케이션 프로세스 종료와 PC 정전의 내구성이 다르다. 정전/OS 장애 후
마지막 커밋이 사라질 수 있으므로 "재시작 시 저장됨"을 "정전에도 주문 ID 보존 보장"으로 확장하지 않는다.
핵심 주문·정지·전송 claim 연결의 FULL 설정/저장장치 전제를 구현 전에 검토한다. 기존 DB 설정은 이번에 변경하지 않는다.
[SQLite 공식 설명](https://www.sqlite.org/pragma.html#pragma_synchronous).

위는 코드 읽기·공식 문서 확인으로 발견한 **도입 전 위험**이다. 이번에 다중 프로세스 사고나
정전 손실을 재현한 것은 아니다. Current C12/C13에 미검증 상태로 남긴다.

## 3. 구조 비교와 권고

| 구조 | 이점 | 한계 / 이번 판단 |
|---|---|---|
| 같은 프로세스의 감시 thread | 변경이 작음 | 매매 프로세스 종료·프로세스 전체 정지에 함께 사라짐. 목표의 독립 감시로 부족 |
| **별도 안전 조정 프로세스 + 분리된 HTTP 작업자** | 매매 계산/HTTP 대기가 멈춰도 시간 검사 가능, 전송 권한 한 곳에서 관리 | IPC·영속 claim·재시작·단일 조정자 검증 필요. **구현 초안 권고** |
| 다른 장비/외부 감시 서비스 | PC 전체 정지에 대한 별도 관측 가능 | 외부 계정/권한/비용/중복 제어 필요. 이번 범위 제외, VPS 구매/배포 없음 |

권고 구조:

```text
기존 매매 계산 ── 목표·의도 ──> 별도 안전 조정자 ── 선기록/claim ──> HTTP 작업자
                                  │                         (한 의도당 한 전송)
                                  ├─ 시간·heartbeat 검사
                                  ├─ WS 힌트 + 별도 원격 조회 결과
                                  └─ 주문/보호/정지 DB + 감사 기록
```

매매 계산 프로세스는 O/v2 선물 주문/스톱 취소를 직접 보내지 않는 경계로 바꿔야 한다.
안전 조정자는 일반 의도와 비상 의도를 모두 중재하되 자기 이벤트 루프에서 HTTP 응답을 기다리지 않는다.
늘리기 HTTP가 진행 중이어도 별도 보호/위험 축소 작업을 검토할 수 있지만, **추가 OPEN은 차단**한다.
독립 감시기와 기존 실행기를 각각 그대로 복제해 동시 실행하는 방식은 채택하지 않는다.

조정자가 죽으면 매매 쪽도 신규 전송을 중단한다. 복구 조정자 하나만 원자적으로 소유권을 얻고,
기존 작업자의 진행 중 주문을 먼저 대조한다. 프로세스 번호만으로 주문 ID를 만들지 않는다.
만료된 lease를 얻었다는 사실만으로 이전 네트워크 요청이 취소됐다고 가정하지 않는다.

O/v2 매매 계산은 하루 한 번 끝나는 작업이지만 안전 조정자는 포지션/미확정 주문이 있는 동안
독립적으로 계속 살아 있어야 한다. 정상적인 일일 계산 종료와 계산 중 heartbeat 소실을 구분한다.
매매 프로세스의 daemon 자식으로 두어 부모 종료와 함께 감시가 사라지게 만들지 않는다.
감시자 자체 heartbeat/기동 확인 실패 때에는 다음 노출 증가를 허용하지 않는다.
RPC 작업자의 기동·초기 연결·시각/필터 준비 시간도 예산에 포함하고, 실제 초기화 실측 전 성능을 단정하지 않는다.
이 상주 수명/예약 연결은 후속 승인 대상이며 이번에 백그라운드 프로그램을 띄우지 않았다.

Windows에서는 spawn 기준으로 모듈 최상위 작업자를 만들고 연결/시계를 명시 주입한다.
DB/HTTP client/잠금을 프로세스 간 공유하지 않는다. 강제 종료 시 공유 queue/lock 손상 가능성을
고려해 작업자별 통신을 격리하고, 통신 결과보다 durable claim과 거래소 대조를 우선한다.
[Python 공식 설명](https://docs.python.org/3/library/multiprocessing.html#contexts-and-start-methods),
[강제 종료 주의](https://docs.python.org/3/library/multiprocessing.html#multiprocessing.Process.terminate).

## 4. 전송 소유권·멱등 계약

1. 계좌 범위는 비밀값이 아닌 `account_scope_id` 별칭 + 환경 + 전략 인스턴스 + 심볼로 구분한다.
   기존 C10을 피하려고 타 전략 미확정 주문을 무시하거나 DB를 임의 통합하지 않는다.
2. 일반 의도 ID는 기존 전략 태그·결정 시각·심볼·목적·방향·명시적 attempt 규칙을 보존한다.
   보호 episode와 안전 action sequence도 영속 기록하며 PID/재시작 시각으로 재생성하지 않는다.
3. 주문 파라미터 hash·episode·세대·ID를 선기록하고 짧은 원자적 transaction에서
   `READY → DISPATCH_CLAIMED`를 한 번만 허용한다. 같은 ID의 다른 파라미터는 오류다.
   손실된 응답/작업자 종료/lease 만료로 DISPATCH_CLAIMED를 READY로 되돌리지 않는다.
4. 네트워크는 transaction **밖**에서 실행한다. claim 성공자만 해당 의도를 단 한 번 POST한다.
   SQLite는 단일 writer이므로 DB busy/claim 실패는 신규 전송 거부이지 보호 시한 정지가 아니다.
   짧은 `BEGIN IMMEDIATE`/CAS 및 연결별 대기 예산을 검토한다.
   [SQLite transaction 규칙](https://www.sqlite.org/lang_transaction.html).
5. 진행 중 작업자의 원격 조회가 "없음"이면 `UNKNOWN/IN_FLIGHT`를 유지한다. 실제 전송 부재를
   입증하기 전 NOT_PLACED·새 attempt·청산 완료로 바꾸지 않는다. 로컬 timeout/프로세스 kill도
   거래소 요청 취소 증거가 아니다. recvWindow만 기다리면 부재 확정된다고 단정하지 않는다.
6. 늦은 응답은 관측 증거로 보관하되 오래된 세대가 HALTED를 해제하거나 새 상태를 덮어쓰지 못한다.
   누적 체결은 감소시키지 않으며, 모순된 수량/종결 상태는 대조 대상으로 둔다.
7. 같은 비상 CLOSE가 UNKNOWN이면 **조회만** 이어 간다. 반면 CLOSE 종결 확인 뒤 늦은 OPEN 체결로
   새 노출이 실제 확인되면, 그 사실에 연결된 별도 위험 축소 의도를 만들 수 있다.
   이는 모르는 청산의 추정 재전송과 구분하며 신규 진입/자동 복귀는 계속 금지한다.

기존 `risk_events`는 감사에 재사용한다. 원자적 소유권/claim에는 기존 주문 원장과 연결되는 최소
상태 저장 확장이 필요하지만, 테이블명/마이그레이션/전송 분리 API는 구현 전 설계 점검에서 확정한다.
이번에는 새 테이블을 만들지 않았다. DB 오류 때 durable claim 없이 추정 비상 POST하는 우회도 만들지 않는다.
DB가 완전히 실패하면 기존 거래소 스톱에 의존하는 한계와 미완료 위험을 critical로 남겨야 한다.

## 5. 보호 판정과 시간 계약

- UTC `_ms`는 저장·거래소 사건 연결에, 실행 중 monotonic 경과는 기한 검사에 사용한다.
  재시작 전 monotonic 값을 새 프로세스와 직접 빼지 않는다. UTC 역행/시각 불명은 정상으로 덮지 않는다.
- `intent_saved_ms`, `dispatch_claimed_ms`, `first_fill_exchange_ms`(없으면 null),
  `fill_observed_ms`, `stop_confirmed_ms`, `halt_observed_ms`, `close_sent_ms`,
  `flat_confirmed_ms`, 시계 품질/관측 출처를 분리한다. exact 체결 공백과 전송 전 기준 보수적 상한은
  별도 이름으로 보고한다. WS/REST의 이벤트 시각·수신 시각을 같은 값으로 위장하지 않는다.
- 중복/역순 TRADE 이벤트의 첫 체결 정보는 주문 ID·체결 식별자·누적 수량과 연결해 보존한다.
  재연결로 놓쳤다면 당시 보수적 시작점을 유지하며 늦은 이벤트로 위반 기록을 삭제하지 않는다.
- 원격 포지션·스톱 조회의 시작/완료/가용 시각을 저장한다. WS는 변화 힌트이며 누락/단절을
  0 포지션으로 취급하지 않는다. 목록 조회 실패는 스톱 없음의 증거도 스톱 있음의 증거도 아니다.
- 보호는 해당 심볼·손실 방향·유효 가격·필수 MARK_PRICE·reduce-only/closePosition 조건과
  실제 수량 커버를 확인한다. 추적하지 않은 외부 스톱을 임의 취소/입양하지 않는다.
  다리 스톱 교체 중에는 어떤 취소가 허용되는지 세대별 소유권으로 제한한다.
- 보호가 확인되면 해당 수량의 창을 종료한다. 증가 후 수량을 이미 closePosition이 덮으면
  단순 HTTP 지연을 새 무보호 체결로 보지 않는다. 확정 미체결도 가짜 포지션으로 만들지 않는다.
- 경과가 5,000ms를 **초과**하면 신규 노출 차단과 영속 HALTED를 기록한다. 확인 가능한 자기
  포지션만 승인된 예외로 축소한다. 포지션 미확인 때는 추정 수량 청산 대신 대조·경고를 계속한다.
- 시계 역행·감시 소실·비정상 상태는 fail-closed지만 그 자체로 보호 공백 시장가 예외를
  확대하지 않는다. 이미 정상 보호 중이면 신규 진입 차단·조회로 처리한다.
- heartbeat/시간 검사 loop 후보 간격은 100ms(실측 전 engineering 초안)다. 위험 한도는 5초 그대로다.
  scheduling 지연이 없다 해도 경계 초과를 다음 tick에 볼 수 있으며 HTTP·DB·알림 시간을 더하면
  늦어질 수 있다. "100ms tick이니 5초 이내 청산 보장"이라는 결론은 금지한다.
- 보호 재시도 3초는 전체 공백 기한을 재설정하지 않는다. 이미 지난 창에 새 3초를 덧붙이지 않는다.
  알림 전송이 막혀도 안전 loop는 계속 돌고 기록/경고 성공 여부를 별도로 남긴다.

## 6. 상태와 복구

| 안전 상태 | 새 노출 | 허용 작업 / 벗어나는 조건 |
|---|---|---|
| RECONCILING | 금지 | 원주문·포지션·보호·소유권 대조, 검증 후 READY 또는 보호 episode |
| READY | 기존 Risk 허용 때만 | 감시/DB/원격 상태 확인 뒤 의도 전송. FULL 위험 규칙 연결은 별도 기존 과제 |
| GUARDING | 추가 OPEN 금지 | 첫/부분체결·보호 확인. 확인되면 READY, 위반하면 HALTED |
| HALTED | 금지 | 자기 포지션 보호·축소·대조만. 날짜/재시작/data/HALT 삭제로 자동 해제 안 됨 |
| CLOSE_UNKNOWN | 금지 | 같은 CLOSE 조회만. 부재/종결 근거 전 새 CLOSE 금지 |
| FLAT_UNSETTLED | 금지 | 현재 0이어도 원래 OPEN/STOP이 진행 중이면 계속 감시 |
| FLAT_HALTED | 금지 | 잔여 주문 종결·보호 정리 후에도 HALTED 유지, 사람 승인 재개 절차는 별도 |

재시작: 신규 전송 차단 → 단일 조정자 소유권 → 진행 중/UNKNOWN 원주문 조회 → 실제 포지션/보호
확인 → 기존 timer/정지 복구 → 잔여 진입·스톱 대조. 부재 한 번·프로세스 종료·queue 비어 있음만으로
원주문이 끝났다고 보지 않는다. "현재 flat"과 "미확정 주문이 없는 최종 flat"도 분리한다.
다른 주체의 주문/포지션이 섞인 심볼은 현행 수동 확인 경계를 유지한다.

## 8. 권고 구현 순서와 이번 완료 경계

1. **다음 Phase 5:** 전송 claim·in-flight 부재 판정·역순 update 방어를 Fake 전용으로 구현/검증.
   C12를 해결하지 않고 기존 manager를 두 프로세스에 나눠 쓰지 않는다. 핵심 기록 내구성 C13도 함께 범위 확정.
2. 조정 loop·HTTP 작업 분리·spawn 종료/재시작 시험. 순수 전략 코어와 별도 execution/ops 계층에 둔다.
3. 동일 snapshot/목표 정상 경로 parity와 기존 보호 회귀 전체 유지. 안전 예외의 차이는 이유를 기록한다.
4. 전체 게이트 통과 후에만 별도 승인으로 O/v2 데모 연결/감시 기동을 검토한다. 실제 거래소 작업은
   Fake 검증에 섞지 않고, 감시 프로세스를 임의 예약하지 않는다.
5. 실거래 승인은 여전히 별개다. 실제 fee/funding 원장·통합 일 손실/DD/지갑 위험 연결도 미완료다.

이번 완료는 문서 설계·코드 근거 읽기·공식 기술 문서 확인·로컬 문서 보존/링크/범위 검사다.

기록이며 이 설계의 실행 검증으로 세지 않는다. 기존 mypy 16오류와 미커밋 보완 파일은 그대로 둔다.
