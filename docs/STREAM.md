# Kafka 스트림 1분봉 (README 5-1)

> 체결 원문을 Kafka 토픽에 그대로 쌓고, Spark Structured Streaming이 **확정된 1분봉만** Delta에 쓴다.
> BTCUSDT 2024-03-01 하루(체결 묶음 1,434,196건)를 중복 · 순서 뒤바뀜을 일부러 섞어 재생했더니 스트림 봉이
> 배치 Gold 봉과 **1,440분 모두 칸마다 같았다.** 워터마크보다 늦게 온 체결이 봉을 바꾸는 것도 보이고,
> 같은 원문 토픽을 더 긴 워터마크로 **다시 읽어** 고쳤다.
> 코드: [`src/mdp/stream/`](../src/mdp/stream)

## 왜 필요한가

배치는 바이낸스가 다음 날 일 파일을 올려야 돈다. 실시간 봉이 필요하면 스트림이 있어야 하는데, 스트림은
**끊기고 · 중복되고 · 늦게 온다.** 그래서 '실시간으로 만들었다'보다 '배치와 같은 답을 내는가'가 중요하다.
여기서는 스트림 봉을 배치 봉과 같은 식으로 만들고, 같은 입력이면 같은 봉이 나오는지 숫자로 확인한다.
날마다 원인을 나눠 기록하는 정식 대사는 다음 단계(5-2)다.

## 흐름

```text
원천                      Kafka 원문 토픽                 Spark Structured Streaming              Delta
바이낸스 WebSocket ──┐     raw.binance.um.aggtrade         1 JSON → 체결 칸(decimal)              gold/stream_bars_1m
(실시간, 키 없음)    ├──▶  받은 그대로 · 받은 시각 ──────▶ 2 워터마크(늦은 체결 버림)   ──MERGE──▶ 확정된 분만
Bronze 체결 재생 ────┘     파티션 1 · 보관 7일              3 (종목, 묶음 번호) 중복 제거             (같은 분은 덮어씀)
(결함 섞기 가능)           오프셋으로 다시 읽기             4 1분 창 집계 = 배치와 같은 함수
                                                            5 워터마크가 분 끝을 지나면 내보냄
```

| 단계 | 하는 일 | 왜 |
|---|---|---|
| 보내기 [`produce.py`](../src/mdp/stream/produce.py) | 받은 글자를 **고치지 않고** 토픽에. 키 = 종목, 메시지 시각 = 받은 시각 | 처리 규칙을 바꾸면 오프셋을 처음으로 돌려 같은 원문으로 다시 만든다(Bronze와 같은 생각) |
| 재생 | Bronze zip을 흘려 읽어 실시간과 **같은 모양** JSON으로. 읽기 직전 SHA-256 재대조 | 키 · 장 시간 없이도 같은 코드를 끝까지 시험. 입력이 배치와 같다고 말할 수 있게 |
| 결함 섞기 [`messages.py`](../src/mdp/stream/messages.py) | n번째마다 **중복**, n번째마다 **지연**(체결 시각보다 늦게, 더 나중 체결 뒤에) | 재연결 · 네트워크 지연을 흉내 — 늘 같은 자리라 다시 돌려도 같음 |
| 워터마크 | '지금까지 본 가장 늦은 체결 시각 − 기다림'보다 이른 체결은 버림 | 그래야 '이 분은 끝났다'고 판단해 봉을 확정하고 상태를 비운다 |
| 중복 제거 | (종목, 묶음 번호, 체결 시각)이 같으면 한 번만 | 체결 시각을 키에 넣어 워터마크가 지난 기억을 지울 수 있게(상태가 끝없이 커지지 않게) |
| 집계 | [`bar_aggregations()`](../src/mdp/gold/bars_1m.py) — **배치 Gold와 같은 함수** | 두 봉의 차이가 '계산 방식'에서 생기지 않게 |
| 쓰기 | 묶음마다 Delta **MERGE** (종목, 분) | Spark는 실패 뒤 같은 묶음을 다시 쓸 수 있다. 덮어쓰기라 다시 써도 같은 결과(정확히 한 번 효과) |

봉 한 줄에는 배치와 같은 값 칸에 더해 `last_received_ms`(그 분 체결을 마지막으로 받은 시각, 신선도용)와
`ids_contiguous`(그 분 안 묶음 번호가 빠짐없이 이어지는가 — 끊김 표시)가 있다.

## 돌려 보기

```bash
docker compose --profile stream up -d          # Kafka 1대 (KRaft, ZooKeeper 없음)
docker compose --profile spark build           # Kafka 커넥터를 넣은 Spark 이미지
# 1) 재생: 하루 + 5분(마지막 분의 워터마크를 넘기려고), 중복 · 지연 섞기
docker compose run --rm spark python -m mdp.stream.produce --source replay --symbol BTCUSDT \
    --start 2024-03-01T00:00 --end 2024-03-02T00:05 --fresh-topic \
    --duplicate-every 997 --delay-every 1009 --delay-ms 5000
# 2) 토픽에 있는 것을 끝까지 처리하고 멈춤
docker compose run --rm spark python -m mdp.stream.bars_1m --trigger available-now --fresh
# 3) 배치 봉과 맞대기 (호스트, Spark 없이 DuckDB)
python -m mdp.stream.check --symbol BTCUSDT --start 2024-03-01T00:00 --end 2024-03-02T00:00
```

실시간(바이낸스 공개 체결, 키 없음)은 `--source live --duration-s 300`, 처리는 `--trigger continuous`.

- Kafka는 컨테이너끼리 `kafka:9092`, 이 PC에서 `127.0.0.1:57092`. 59092 등 Windows(Hyper-V)가 잡아 둔 포트
  범위가 있어 비어 있는 57092를 골랐다(`netsh interface ipv4 show excludedportrange protocol=tcp`).
- Bronze를 다른 디스크에 두었다면 재생 전에 `MDP_BRONZE_ROOT`를 설정한다(Airflow와 같음).

## 결과 1 — 같은 원문이면 같은 봉 (BTCUSDT 2024-03-01, 2026-10-24 한국 시각)

| 단계 | 값 |
|---|---|
| 재생 | 보낸 메시지 1,439,315 = 원래 체결 1,437,874(3/1 하루 1,434,196 + 3/2 첫 5분, 그중 1,425건은 지연) + 중복 1,441 · **21초 (초당 약 6.8만)** |
| 스트림 처리 | 묶음 9개(묶음당 최대 20만 메시지) · 받은 줄 1,439,315 · 워터마크로 버림 0 · **약 2.5분** (컨테이너 띄우기 포함) |
| 쓴 봉 | 1,443 = 3/1의 1,440 + 3/2 00:00~00:02 (재생 끝 00:05 − 워터마크 1분 → 00:03 이후는 아직 미확정) |
| 배치 Gold와 맞대기 | **1,440분 모두 있고, 12개 값 칸 모두 같음** · 배치에만 0 · 스트림에만 0 |

- 중복 1,441건은 봉에 한 번만 들어갔고, 5초 늦게 온 1,425건은 워터마크(1분) 안이라 모두 제자리 봉에 들어갔다.
- 재생 끝 이후의 분이 '없음'인 것이 정상이다 — 체결이 더 올 수 있는 분은 쓰지 않는다.

## 결과 2 — 워터마크보다 늦으면 봉이 바뀐다, 원문을 다시 읽어 고친다

1009번째 체결마다 **10분** 늦게 보내고(1,438건), 같은 토픽을 워터마크만 바꿔 두 번 처리했다(묶음당 최대 2만
메시지 — 하루치가 74개 묶음, 묶음 하나가 약 20분 치). 재생은 3/2 00:20까지(15분 워터마크로도 3/1 마지막 분이
확정되게).

| | 워터마크 1분 | 같은 토픽 다시 읽기 — 워터마크 15분 |
|---|---:|---:|
| 받은 메시지 · 묶음 | 1,451,634 · 74 | 1,451,634 · 74 |
| 늦어서 버림 | **65** | 0 |
| 배치와 같은 분 | **1,414** / 1,440 | **1,440** / 1,440 |
| 다른 칸 | 거래량 · 거래대금 · 체결 수 26분, 공격 매수량 23분 · **시고저종은 0** | 없음 |
| 처리 시간 | 12.6분 | 18.2분 |

- 다른 26분은 스트림 봉의 `ids_contiguous`(그 분 안 묶음 번호가 빠짐없이 이어지는가)가 **정확히 그 26분만
  거짓**이었고, 그 분들에서 빠진 묶음 수 합계가 버린 65건과 같았다(Delta 시간여행으로 1분 실행 직후 버전을 열어
  확인). 배치 Gold는 3월 1일 1,440분 모두 이어져 있다. 즉 **스트림만 보고도 '이 분은 체결이 빠졌다'를 안다.**
- 시고저종이 같았던 것은 버려진 체결이 그 분의 처음 · 끝 · 최고 · 최저가 아니었기 때문이다(늘 그렇지는 않다).
- 원문 토픽에 받은 그대로 있으니, **처리 규칙(워터마크)만 바꿔 같은 원문을 처음부터 다시 읽어** 고칠 수 있다.
  Bronze에서 Silver를 다시 만드는 것과 같은 생각이다.
- 묶음이 작을수록 묶음마다 드는 고정 비용(Delta MERGE · 체크포인트 쓰기, Windows 폴더 연결 위)이 커서 결과 1
  (묶음 9개, 2.5분)보다 훨씬 느렸다. 워터마크가 길면 기억할 상태가 커져 더 느리다.

**늦음은 언제 판정되나 (Spark의 실제 동작)** — 시험을 만들다 확인한 것: 상태 연산자가 둘(중복 제거 · 집계)이면
Spark는 묶음 k의 체결이 늦었는지를 **바로 앞 묶음의 워터마크**와 비교한다. 그래서 실제로 기다려 주는 시간은
'워터마크 + 묶음 하나'쯤이다. 실시간에서는 묶음 하나가 수 초 치라 차이가 작지만, 재생을 최대 속도로 하면 묶음
하나가 수십 분 치라 같은 10분 지연도 묶음 경계를 넘을 때만 버려진다(그래서 1,438건 중 65건만 버려졌다). 실시간에
가까운 숫자를 보려면 `--speed`로 재생을 늦추고 `--trigger continuous`로 처리한다.

**워터마크를 얼마로 둘까** — 길게 두면 늦은 체결을 더 받지만 봉 확정이 그만큼 늦고 기억할 상태가 커진다.
짧게 두면 빠르지만 늦은 체결을 잃는다. 잃은 것은 대사(5-2)가 찾아 배치 봉으로 바꿔 넣는 것이 이 설계의 답이다.

## 결과 3 — 실시간 (바이낸스 공개 체결, 키 없음, 2026-10-23 17:52 UTC 부근)

| 항목 | 값 |
|---|---|
| 받은 체결 | 200초에 925건 (끊김 0) |
| 확정된 봉 | 3개 (17:52 · 17:53 · 17:54) — 17:55 이후는 워터마크 대기 |
| 원문에만 있는 칸 | `nq`, `st` — 아카이브에 없는 칸이라 뜻을 확인하지 못했다(확인 필요). 처리 쪽은 무시한다 |

- **예전 주소는 연결만 되고 체결이 0건이었다.** 바이낸스가 2026-03 공지로 선물 WebSocket 주소를 용도별
  (`/public` · `/market` · `/private`)로 나눴고, aggTrade는 `/market` 이다
  (`wss://fstream.binance.com/market/ws/btcusdt@aggTrade`). 연결 성공 ≠ 데이터 받음 — '받은 건수 0'을 실패로
  보는 감시가 필요하다(5-2에서 신선도로).
- 첫 봉(17:52)은 받기 시작한 뒤의 체결만 있는 **반쪽 봉**인데 `ids_contiguous`는 참이다 — 그 분 안의 번호는
  이어져 있기 때문이다. 시작 · 재연결 경계의 봉은 앞 봉과의 번호 연결로 따로 가려야 한다(5-2).
- 살펴본 메시지 하나는 받은 시각(이 PC)이 체결 시각(바이낸스)보다 0.2초, 이벤트 시각보다 0.35초 **이르게**
  찍혔다 — 이 PC(WSL) 시계가 바이낸스보다 뒤처져 있다는 뜻이다(여러 건으로 재지는 않음). 신선도(받은 시각 − 체결 시각)를 잴 때는 시계 차이를 먼저 확인해야 한다.

## 남은 것 · 확인 필요

- 실시간 메시지 칸의 뜻이 아카이브 칸과 같은지는 같은 날 일 파일과 맞대어 확인한다 — 대사 코드(5-2,
  [기록](RECONCILE.md))는 있고, 실시간 하루치로는 아직 돌리지 않았다. 그 전까지 '확인 필요'.
- 실시간 연결 한도 · 24시간 끊김 같은 규칙은 바이낸스 문서로 확인하지 못했다(확인 필요). 주소는 `--url`로 바꿀
  수 있다.
- 칸이 빠진 메시지는 지금은 버리기만 한다(격리 표로 남기지 않음).
- 실행 기록의 최대 메모리는 파이썬 프로세스 값이다 — Spark(JVM) 메모리는 들어 있지 않다.
