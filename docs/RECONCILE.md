# 매일 대사 — 스트림 봉 = 배치 봉 (README 5-2)

> 같은 날의 스트림 1분봉과 배치 1분봉을 분마다 맞대고, 다르면 **원인을 나눠** PostgreSQL에 남기고,
> 원하면 배치 봉으로 **메운다.** PC 잠듦 · 늦은 도착 · 중복을 일부러 섞은 하루(BTCUSDT 2024-03-01)에서
> 원인별 숫자가 **보낸 쪽 · Spark가 따로 센 숫자와 정확히 같았다** (받지 못한 체결 13,897 = 재생이 건너뛴
> 13,897, 늦어서 빠진 체결 678 = Spark가 워터마크로 버린 678).
> 코드: [`src/mdp/reconcile/daily.py`](../src/mdp/reconcile/daily.py) · 표: [`005_reconcile.sql`](../src/mdp/runlog/sql/005_reconcile.sql)

## 왜 필요한가

PC가 늘 켜져 있지 않으니 스트림은 **반드시 끊긴다.** 그래서 목표는 '24시간 무중단'이 아니라 **빈 곳을 정확히
찾아 메우기**다(그림 4). '다르다'만으로는 고칠 수 없다 — 원인에 따라 할 일이 다르다.

| 원인 | 뜻 | 할 일 |
|---|---|---|
| `stream_gap` | 그 분 체결 중 **원문 토픽에 없는 것**이 있음 (끊김 · PC 잠듦 · 받기 시작 전) | 감시 · 재연결, 배치로 메우기 |
| `late` | 빠진 체결이 **모두 원문 토픽에는 있음** — 받았지만 워터마크 뒤라 버림 | 워터마크 조정, 또는 원문 다시 읽기 |
| `duplicate` | 스트림이 배치보다 체결을 더 셈 | 중복 제거 코드 확인 |
| `other` | 체결 수는 같은데 값이 다름 | 사람이 확인 |

## 어떻게 원인을 나누나

```text
배치 봉(일 파일 → Silver → Gold)  ─┐
스트림 봉(gold/stream_bars_1m)      ├─▶ 분마다 맞대기 ─▶ 같음 → matched (메운 분이면 repaired)
                                   │                  다름 → 빠진 묶음 = 배치 묶음 수 − 스트림 묶음 수
Silver 그날 체결 번호 ──┐          │                         └ 그중 원문 토픽에 없는 것 = not_received
원문 토픽 받은 번호 ────┴─ 빼기 ───┘                           나머지(받았는데 빠짐) = late_trades
```

- 체결 번호를 봉에 하나하나 남기지 않아도 된다: **빠진 수**는 두 봉의 묶음 수 차이로, **받지 못한 수**는
  Silver 체결 번호 − 원문 토픽 번호로 알 수 있고, 나머지가 늦어서 버린 수다.
- 이것이 되는 이유는 원문 토픽이 '받은 그대로'이기 때문이다(5-1). 보관 7일 안에 대사해야 한다.
- 스트림 봉과 배치 봉은 **같은 집계 함수**로 만들었으므로, 차이는 입력에서만 생긴다고 볼 수 있다.

**메우기(`--repair`)** — 원인이 있는 분의 스트림 봉을 배치 봉으로 MERGE하고 `repaired = true`로 표시한다.
배치 봉은 바이낸스 일 파일에서 만든 확정된 답이다. 바꾸기 전 스트림 봉은 Delta 이력에 남는다(시간여행).
다음 대사에서 그 분은 `repaired`로 세고, **일치율에는 넣지 않는다** — 스트림이 맞힌 것이 아니므로.

**결과 표 (PostgreSQL, 더하기만)** — 대사 한 번 = `reconcile_daily` 한 줄, 다른 분 = `reconcile_minutes` 한 줄.
지우거나 고치지 않으므로 '메우기 전에 찾은 원인'과 '메운 뒤 상태'가 둘 다 남는다. 그날의 마지막 결과는 뷰
`reconcile_daily_latest`. 체크 제약으로 `matched + repaired + 원인들 = 배치 분 수`를 DB가 지킨다.

## 시연 — BTCUSDT 2024-03-01

재생에 섞은 결함 (늘 같은 자리):

| 결함 | 설정 | 흉내 내는 것 |
|---|---|---|
| 빈 곳 | 10:00:30 ~ 10:20:30 체결을 보내지 않음 (13,897건) | PC 잠듦 · 연결 끊김 |
| 늦음 | 1009번째마다 30분 늦게 (1,411건) | 네트워크 지연 |
| 중복 | 997번째마다 한 번 더 (1,427건) | 재연결 때 같은 체결 두 번 |

```bash
docker compose run --rm spark python -m mdp.stream.produce --source replay --symbol BTCUSDT \
    --start 2024-03-01T00:00 --end 2024-03-02T00:05 --fresh-topic \
    --duplicate-every 997 --delay-every 1009 --delay-ms 1800000 \
    --gap-from 2024-03-01T10:00:30 --gap-to 2024-03-01T10:20:30
docker compose run --rm spark python -m mdp.stream.bars_1m --trigger available-now --fresh --max-offsets 20000
docker compose run --rm spark python -m mdp.reconcile.daily --symbol BTCUSDT --date 2024-03-01 --repair
docker compose run --rm spark python -m mdp.reconcile.daily --symbol BTCUSDT --date 2024-03-01
```

| | 대사 1 (`--repair`) | 대사 2 (메운 뒤) |
|---|---:|---:|
| 배치 분 · 스트림 분 | 1,440 · 1,421 | 1,440 · 1,440 |
| `matched` | 993 | 993 |
| `stream_gap` | **21분** (10:00 ~ 10:20) | 0 |
| `late` | **426분** | 0 |
| `duplicate` · `other` | 0 · 0 | 0 · 0 |
| `repaired` | 0 (이번에 메움 447) | **447** |
| 받지 못한 체결 · 늦어서 빠진 체결 | **13,897 · 678** | 0 · 0 |
| 일치율 (스트림 몫) | 68.96% | 68.96% |
| 걸린 시간 | 2분 | 1.4분 |

**숫자 맞추기 — 대사가 센 원인이 맞는가:**
- 받지 못한 체결 13,897 = 재생이 빈 곳에서 **보내지 않은** 메시지 13,897 (보내는 쪽 기록).
- 늦어서 빠진 체결 678 = Spark가 스트림 처리 중 **워터마크로 버렸다고 보고한** 줄 678 (`numRowsDroppedByWatermark`).
- 중복 1,427건은 스트림의 중복 제거가 모두 걸러 `duplicate` 0.
- 빈 곳 양 끝 10:00 · 10:20은 반쪽 봉(771건 중 413건 · 1,395건 중 850건)이었고, 원문에 없는 체결이 있어
  `stream_gap`으로 맞게 나뉘었다. 가운데 19분은 스트림 봉 자체가 없었다.

**같은 원문, 묶음 크기만 다르게** — 같은 토픽을 묶음당 20만 메시지로 처리했을 때는 30분 지연이 하나도 버려지지
않아(`late` 0) 일치율이 98.54%(`stream_gap` 21분만)였다. 묶음 하나가 약 3시간 치라 워터마크가 묶음 사이에서만
크게 움직이기 때문이다(5-1 [기록](STREAM.md)의 '늦음은 언제 판정되나'). 묶음당 2만으로 줄이자 실시간에 가까워져
678건이 버려졌다. 대사가 없었다면 이 차이를 알 수 없었다.

- 이 시연의 스트림 처리(묶음 73개)는 29분 걸렸다 — 묶음마다 Delta MERGE · 체크포인트를 Windows 폴더 연결 위에
  쓰는 고정 비용 때문이다. 실시간에서는 묶음이 10초마다 하나라 문제가 되지 않는다.
- PostgreSQL에는 이 시연 앞에 돌린 묶음 20만 시연의 두 줄도 남아 있다. 그중 메운 뒤 줄의 '받지 못한 체결'이
  13,897로 남은 것은 메운 분까지 세던 버그 때문이었고, 고친 뒤 위 시연을 다시 돌렸다(더하기만 하는 표라 그대로 둠).

## 남은 것 · 확인 필요

- **실시간 데이터로 대사하기**: 실시간으로 하루를 받은 뒤 다음 날 일 파일이 나오면 `mdp.bronze.sync`로 받아
  Silver → Gold → 대사한다. 그래야 실시간 메시지 칸의 뜻(5-1의 '확인 필요')과 받은 시각 지연(`ingest_lag_*`, live만)이
  실제 값으로 채워진다. 아직 하지 않았다.
- 매일 자동으로 돌리는 Airflow DAG(일 파일 받기 → Silver → Gold → 대사)는 아직 없다 — 지금은 명령으로 돈다.
- 배치에도 없는 분(바이낸스 일 파일 자체의 빈 곳)은 Silver 감사(`agg_trades_gaps`)가 따로 잡는다. 대사는 배치를 정답으로 본다.
