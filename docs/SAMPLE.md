# 키 없는 샘플 시연 (README 6-1)

> 거래소 키도, 850MB 내려받기도 없이 **명령 하나로** 파이프라인 전체를 돌린다. 합성 종목 `DEMOUSDT` 3일치를
> 바이낸스 아카이브와 같은 모양으로 만들고 결함 5종을 정해진 자리에 넣은 뒤, 평소 명령으로 Silver → 검산 →
> Gold → PostgreSQL → Kafka 스트림 → 대사를 돌리고, **넣은 결함을 빠짐없이 · 더하지도 않고 찾았는지**
> 정답지와 맞춘다. 결과: **12/12 맞음, 107초.**
> 코드: [`src/mdp/sample/`](../src/mdp/sample)

## 돌려 보기

준비물: Python 3.11+, Docker Desktop (메모리 8GB 이상 권장).

```bash
pip install -e ".[dev,lake]"
python -m mdp.sample.demo                # 배치만: 약 1분 (+ 처음 한 번 Spark 이미지 만들기 몇 분)
python -m mdp.sample.demo --with-stream  # + Kafka 재생 · 스트림 봉 · 대사: 약 2분
```

- 모든 것은 `data/sample/` 아래에만 쓴다(진짜 레이크 `data/lake`와 진짜 원문 토픽은 건드리지 않음).
  PostgreSQL에는 종목 `DEMOUSDT`로만 쓴다.
- 다시 돌리면 이전 샘플을 지우고 처음부터 만든다. 지우기 전에 그 폴더가 저장소 `data/` 아래이고 정답지
  (`expected.json`)가 있는지 확인한다 — 엉뚱한 폴더를 지우지 않게.

## 왜 합성 데이터인가

- **누구나 돌려 볼 수 있게**: 진짜 데이터는 한 달 체결 zip만 850MB이고, 원천 데이터의 재배포 조건은 확인
  전이라(확인 필요) 저장소에 넣을 수 없다. 합성 데이터는 몇 초 만에 만들어지고 몇 번 만들어도 **같은 바이트**
  (같은 SHA-256)다 — zip 안 파일 시각까지 고정했다.
- **감사가 일하는 것을 보여 주려고**: 진짜 2024-03은 결함이 0개라 감사 규칙이 무엇을 잡는지 보이지 않는다.
  합성 데이터는 결함을 어디에 몇 개 넣었는지 알기 때문에, 결과를 **정답과 숫자로** 맞출 수 있다.
- **시연 전용 코드를 두지 않으려고**: 시연기는 순서만 알고, 각 단계는 진짜 데이터에 쓰는 명령 그대로다.
  다른 것은 레이크 위치(환경 변수)와 종목뿐이다.

## 넣은 결함과 정답

시장: 3일(2024-01-01 ~ 03) · 매분 체결 5~24묶음(빈 분 없음) · 가격은 0.1 단위로 걷는다 · 62,132묶음.
공식 1분봉은 **결함을 넣기 전** 진짜 체결로 계산한다(바이낸스가 올린 봉 역할). 결함은 2일째 체결 파일에만 넣는다.

| 결함 | 자리 | 정답 | 실제 |
|---|---|---|---|
| 빈 곳 | 10:00 분의 묶음 5개를 뺌 | 빈 곳 표에 (1029423, 1029429, 5) | 같음 |
| 같은 내용 중복 | 11:00 분 처음 3개를 한 번씩 더 | 하나만 남김 | 같음 |
| 다른 내용 중복 | 15:00 분 한 묶음을 가격만 바꿔 한 번 더 | 두 줄 다 격리 `conflicting_duplicate` | 같음 |
| 못 읽는 줄 | 12:00 분 사이 한 줄 | 격리 `parse_error` | 같음 |
| 기간 밖 줄 | 파일 끝에 3일째 첫 체결 | 격리 `outside_period` | 같음 |

정답지(`data/sample/expected.json`)는 데이터를 만든 쪽이 적고, 확인은 **DuckDB가 Delta 표를 직접 읽어** 한다
(만든 엔진 Spark와 확인하는 엔진을 다르게). 확인표:

| 확인 | 정답 = 실제 |
|---|---|
| Silver 깨끗한 체결 | 62,126 (= 62,132 − 빈 곳 5 − 다른 내용 중복 1) |
| 격리 | `parse_error` 1 · `conflicting_duplicate` 2 · `outside_period` 1 |
| 중복 줄 (같은 번호가 또 나온 줄) | 4 (같은 내용 3 + 다른 내용 1) |
| 빈 곳 · 시각 역행 | 1곳 (1029423 → 1029429, 5개) · 0 |
| 의심일 · 날 안에서 빠진 번호 | 2024-01-02 · 6 |
| Gold 1분봉 | 4,320 (3일 × 1,440) |
| Gold = 공식 봉 (칸마다 같은 분) | 1일 1,440 · **2일 1,438** · 3일 1,440 |
| 공식 봉 − Gold 거래량 | 5.791 (빠진 6묶음의 수량 합) |
| PostgreSQL 복사본 | 4,320행 (양쪽 SHA-256 같음) |
| 대사 (`--with-stream`) | 끊김 6분 · 받지 못한 체결 76 · 늦음 0 · 중복 0 · 기타 0 |

- 2일째 Gold가 공식 봉과 다른 2분(10:00 · 15:00)은 결함 때문에 빠진 체결이 있는 바로 그 분이다.
- 스트림 단계는 1일째를 Kafka로 보내되 12:00:30 ~ 12:05:30은 보내지 않고(PC 잠듦) 97번째마다 중복을 섞는다.
  대사가 끊김을 6분(12:00 ~ 12:05) · 76묶음으로 정확히 찾고, 중복은 스트림이 모두 걸러 0이다. 그 6분은 배치
  봉으로 메운다.

**만들다 알게 된 것** — 처음 정답지에는 '중복 줄 3'이라고 적었는데 Silver는 4라고 했다. Silver의 중복 줄 수는
`줄 수 − 서로 다른 번호 수`라서 다른 내용 중복의 두 번째 줄도 센다(코드 정의대로). 파이프라인이 아니라 정답지를
고쳤다. 또 DuckDB 검산은 '빈 곳 2곳 · 6개'를 보고하는데, Spark의 파일별 빈 곳 표는 '1곳 · 5개'다 — DuckDB는
깨끗한 체결(격리 뒤)을, Spark는 원본 파일(격리 전)을 보기 때문이다. 다른 내용 중복으로 격리된 번호 하나가 그 차이다.

## 걸린 시간 (단일 PC, 2026-10-24)

| 단계 | 초 |
|---|---:|
| 합성 Bronze 만들기 | 1 |
| Silver (Spark 컨테이너) | 33 |
| Silver 검산 (DuckDB) | 1 |
| Gold (Spark 컨테이너) | 19 |
| PostgreSQL 복사 | 2 |
| Kafka 재생 · 스트림 봉 · 대사 | 2 · 25 · 23 |
| 정답 맞추기 | 1 |
| **합계** (PostgreSQL · Kafka 켜기 포함) | **107** |

Spark 단계 시간의 대부분은 컨테이너 · JVM을 띄우는 시간이다(데이터는 6만 묶음).
