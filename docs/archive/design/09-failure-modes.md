# 09 — 가장 위험한 기술적 실패 지점 (K)

평가 축: **발생 확률 × 손실 규모 × 탐지 난이도**.
"조용히 잘못되는 것"이 "시끄럽게 죽는 것"보다 위험하다.

## Tier 1 — 계좌를 날릴 수 있는 것

### F1. 보호주문 없는 포지션 (UNPROTECTED)

| | |
|---|---|
| 시나리오 | 진입 체결 직후 스톱 등록 전에 프로세스 crash / 네트워크 단절 / API 오류 |
| 손실 | **무한** (레버리지 × 급락). 최악의 경우 강제청산 |
| 확률 | 중간 (창은 수백 ms 지만 누적 노출은 거래 수에 비례) |
| 탐지 | 중간 — 포지션은 조용히 존재한다 |
| 대응 | ① `closePosition=true` 스톱을 첫 체결 즉시 등록 ② 등록 실패 N회 → 즉시 시장가 청산 ③ `max_unprotected_ms` 초과 시 청산 ④ **별도 프로세스 워치독**이 5초마다 INV-1 검증 ⑤ 기동 시 reconcile 에서 최우선 검사 |

> 이것이 1위인 이유: 다른 모든 실패는 "얼마나 잃느냐"의 문제지만, 이것은 "다 잃느냐"의 문제다.

### F2. 재시작으로 인한 중복 진입

| | |
|---|---|
| 시나리오 | 주문 전송 후 DB 기록 전 crash → 재시작 시 "포지션 없음"으로 판단하고 재진입 |
| 손실 | 의도의 2~N배 노출. 리스크 모델 전면 무효 |
| 확률 | 높음 (재시작은 일상) |
| 탐지 | 쉬움 (사후) / 어려움 (사전) |
| 대응 | ① **결정론적 `clientOrderId`** — 거래소가 중복을 거부 (구조적 차단) ② 기동 시 거래소 우선 reconcile ③ INV-4 (심볼당 활성 포지션 1개) ④ 진입 전 로컬+원격 2단 검사 |

### F3. 주문 응답 유실 후 맹목적 재시도

| | |
|---|---|
| 시나리오 | POST 타임아웃 → 실제로는 체결됨 → 재시도 → 2배 포지션 |
| 손실 | F2와 동일 |
| 확률 | 중간~높음 (타임아웃은 흔하다) |
| 탐지 | 어려움 |
| 대응 | ① `UNKNOWN` 상태를 상태머신에 **명시적으로 모델링** ② 재시도 전 `origClientOrderId` 로 조회 필수 ③ UNKNOWN 미해소 시 신규 진입 전면 금지 (G1.3) ④ 같은 `clientOrderId` 재전송은 안전 (거래소가 거부) |

### F4. 청산가가 손절가보다 가까움

| | |
|---|---|
| 시나리오 | 레버리지·증거금 설정 오류로 스톱 도달 전에 강제청산 |
| 손실 | 계획된 0.5%가 아니라 증거금 전액 |
| 확률 | 낮음 (설정 오류 시) / 치명적 |
| 탐지 | 사전 계산 가능 |
| 대응 | ① 게이트 G4.8: `liq_distance >= 2 × stop_distance` 아니면 진입 거부 ② Isolated margin ③ 백테스트에서 청산 1회라도 발생하면 파라미터 실격 ④ config 스키마로 레버리지 상한 강제 |

### F5. 설정 오타

| | |
|---|---|
| 시나리오 | `risk_per_trade_pct: 0.5` 를 "0.5%"로 의도했는데 코드는 50%로 해석. 또는 `max_leverage: 100` |
| 손실 | 단 한 번의 거래로 계좌 소멸 가능 |
| 확률 | 중간 (사람은 실수한다) |
| 대응 | ① **pydantic 스키마로 범위 검증** (`risk_per_trade_pct: float = Field(gt=0, le=0.02)`) ② 단위를 이름에 명시 (`_pct`, `_bps`, `_ms`) ③ 기동 시 설정 요약을 Telegram 으로 전송하고 live 모드는 사람 확인 필요 ④ live 설정 변경 시 diff 를 알림 |

## Tier 2 — 전략을 무의미하게 만드는 것

### F6. 백테스트-실거래 로직 분기 (silent divergence)

| | |
|---|---|
| 시나리오 | 성능 최적화, 리팩터링, 조건문 추가로 두 경로가 미묘하게 달라짐 |
| 손실 | 검증된 적 없는 전략으로 실거래 (= 무작위 매매) |
| 확률 | **높음** (시간이 지날수록 필연적) |
| 탐지 | **매우 어려움** — 겉으로는 잘 돌아간다 |
| 대응 | ① `decide()` 단일 함수 공유 (구조적) ② `import-linter` 로 의존 방향 강제 ③ **일일 Parity Test** (→ 07 §6.1) ④ Decision 해시 비교, 불일치 1건도 critical |

### F7. Look-ahead / future leakage

| | |
|---|---|
| 시나리오 | 전체 표본 정규화, repainting ZigZag, 미마감 봉 사용, 수정된 거시 데이터 사용 |
| 손실 | 백테스트는 훌륭한데 실거래는 손실 — 가장 흔한 실패 |
| 확률 | **매우 높음** |
| 탐지 | 어려움 (코드 리뷰로는 잘 안 잡힘) |
| 대응 | ① `SnapshotBuilder` 단일 관문 ② `causal_zscore` 만 사용, 전역 scaler 금지 ③ **1봉 지연 테스트**와 **신호 셔플 테스트** (→ 07 §5.4) ④ `vintage_ms` 필터 ⑤ ZigZag `confirmed_at` 모델링 |

### F8. 과최적화

| | |
|---|---|
| 시나리오 | 지표 15개 × TF 6개 가중치를 백테스트로 튜닝 |
| 손실 | 실거래에서 성과 소멸 |
| 확률 | **매우 높음** (의도적으로 저항하지 않으면 확정) |
| 대응 | ① feature 5개로 시작 ② 등가중 기준선 ③ TEST 구간 1회만 ④ walk-forward ⑤ Deflated Sharpe ⑥ 파라미터 섭동 테스트 ⑦ **시도 횟수를 DB에 기록** |

### F9. 잘못된 시장 데이터

| | |
|---|---|
| 시나리오 | 0/음수 가격, O-H-L-C 관계 위반, 중복 봉, 시각 어긋남, 거래소 오류 틱 |
| 손실 | 지표 폭주 → 비정상 사이즈 주문, 스톱 오발동 |
| 확률 | 중간 |
| 대응 | ① `marketdata/integrity.py` 에서 수집 시점 검증 (`low <= min(o,c) <= max(o,c) <= high`, 가격>0, 시각 정렬) ② 직전 대비 변화율 임계 ③ 이상치 발견 시 저장하되 `quarantine` 표시 + DEGRADED ④ 게이트 G2.4 |

### F10. 부동소수점 / 정밀도 오류

| | |
|---|---|
| 시나리오 | `float` 로 수량 계산 → `stepSize` 불일치 → 주문 거부, 또는 청산 후 dust 잔량이 남아 "포지션 있음"으로 오판 |
| 손실 | 주문 실패 / 상태 오판 / 의도치 않은 잔여 노출 |
| 확률 | 높음 |
| 대응 | ① `Decimal` 전면 사용, DB에 문자열 저장 ② `floor_to_step` 은 항상 **내림** ③ dust 임계값 정의: `|qty| < step_size` 는 FLAT 으로 간주 ④ 청산은 `closePosition=true` 사용 |

## Tier 3 — 운영을 방해하는 것

### F11. WebSocket 단절 / 이벤트 유실

| 대응 | `listenKey` 60분 연장, 하트비트 감시, 단절 즉시 DEGRADED, 재연결 후 REST 갭 보정, 시퀀스 검증 |

### F12. Rate limit / IP ban

| 대응 | `X-MBX-USED-WEIGHT-1M` 선제 감속, 토큰 버킷, 요청 우선순위(주문·조회 > 캔들), 429/418 시 지수 백오프 + DEGRADED, 벌크 데이터는 REST 대신 파일 다운로드 |

### F13. 거래소 유지보수 / 심볼 상태 변경

| 대응 | `exchangeInfo.status != TRADING` 이면 진입 금지. 유지보수 공지 감지 시 보수적으로 포지션 축소 |

### F14. 부분 체결 처리 오류

| 대응 | `fills` 를 개별 이벤트로 저장(`exchange_trade_id` UNIQUE), 포지션 수량은 fills 합계로 재계산, 보호주문은 `closePosition=true` 로 수량 무관하게 동작, 미체결 잔량은 타임아웃 후 취소 |

### F15. DB 잠금 / 디스크 가득 참

| 대응 | WAL + `busy_timeout`, 쓰기 단일 스레드, 디스크 여유 감시(임계 미만 시 DEGRADED), **DB 장애가 청산을 막지 않도록** 보호주문은 이미 거래소에 있음 |

### F16. LLM / 뉴스 / 거시 API 장애

| 대응 | 전부 **비동기 부가 경로**. 타임아웃 시 해당 요소 비활성(0 기여가 아니라 비활성). 매매 루프와 손절은 무영향. 원 명세 §10 요구사항 충족 |

### F17. 시각 drift / 캔들 경계 오판

| 대응 | `chrony` 필수, 기동 시 및 주기적 서버 시각 대조, drift > 1s 경고 / > 5s 거래 중단, 모든 시각 UTC epoch ms, 봉 마감 판정은 **거래소가 준 `closed` 플래그** 우선 |

### F18. 프로세스 crash / 서버 reboot

| 대응 | `systemd Restart=always`, 기동 시 전체 reconcile, 재시작 횟수 감시(짧은 시간에 반복 재시작 = crash loop → 거래 중단하고 알림만), 거래소 스톱은 그동안에도 유효 |

### F19. 극단 슬리피지

| 대응 | 시장가 주문 전 호가 스프레드 확인(G2.5), 변동성 게이트(G5.1), 주문 크기를 최근 거래량 대비 제한, 체결 후 슬리피지 실측 기록 → 임계 초과 시 알림 |

### F20. 사람의 개입과 시스템의 충돌

| 시나리오 | 사용자가 앱에서 수동으로 포지션을 닫거나 주문을 넣음 |
| 대응 | reconcile 이 외부 주문을 감지하면 **임의로 취소하지 않고** HALTED + 알림 (→ 04 §4.2 #6). 우리 `clientOrderId` prefix 로 소유권 구분 |

## 탐지 우선순위 요약

가장 무서운 것은 **조용한 실패**다. 다음 3가지는 자동 탐지 장치를 반드시 만든다:

| 실패 | 자동 탐지 장치 | 주기 |
|---|---|---|
| F1 보호주문 부재 | 워치독의 INV-1 검증 | 5초 |
| F6 로직 분기 | Parity Test | 일 1회 |
| F7 look-ahead | 1봉 지연 + 신호 셔플 테스트 | 백테스트마다 (CI) |

## 설계 원칙 (실패 대응 총론)

1. **거래 실패 시 무조건 재주문하지 않는다.** 먼저 거래소에 실제 상태를 묻는다
2. **모호하면 진입하지 않는다.** 모호하면 청산은 한다 (비대칭 처리)
3. **안전 방향 동작은 어떤 상태에서도 막히지 않는다**
4. **모든 이상은 DB에 기록**한다. 로그만 남기면 사라진다
5. **자동 복구는 읽기·검증까지만.** 자금이 움직이는 복구는 보수적 기본값(청산) 또는 사람 승인
