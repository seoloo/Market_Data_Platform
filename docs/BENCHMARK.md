# 벤치마크 — 연구 스크립트 · DuckDB · Spark (README 4-3)

> 같은 체결 월 파일을 네 방법으로 처리해 **같은 답을 내는지**, 그때 **시간과 메모리**가 얼마인지 쟀다.
> 코드: [`src/mdp/bench/`](../src/mdp/bench) · 실행: `python -m mdp.bench.main --symbol BTCUSDT --month 2024-03 --rounds 2`

## 과제 (네 방법 모두 같은 일)

BTCUSDT 선물 체결 월 파일 2024-03 하나(zip 847MB · 압축 해제 4.4GB · **66,512,993행**)에서
연구 216 추출기가 뽑던 값을 그대로 뽑는다.

- 행 수 · 첫/끝 번호 · 첫/끝 시각
- 빈 곳(빠진 번호) 위치 · 중복 줄 수 · 시각 역행 수
- 매시 00분 점검값 744개 `[거래량, 공격 매수량, 체결 수]`
- 5분마다 첫 10초 창 8,928개 `[공격 매수량, 공격 매도량, 체결 수]`

정해 둔 결과 모양과 비교 규칙: [`mdp.bench.result`](../src/mdp/bench/result.py). 정수는 정확히, 소수는 상대 오차 1e-9 안.

## 결과

| 방법 | 읽는 것 | 걸린 시간 (1판 / 2판) | 최대 메모리 | 정답지와 |
|---|---|---:|---:|---|
| 연구 전수 추출 `legacy-full` (정답지) | zip 직접 | 133.9초 / 144.5초 | **30MiB** | — |
| 연구 빠른 추출 `legacy-fast` (연구에서 쓴 것) | zip 직접 | 17.1초 / 17.5초 | 214MiB | ❌ 1분 다름 |
| **DuckDB** (8스레드, 메모리 한도 8GB) | 압축 푼 CSV | **11.6초 / 12.3초** | 4.4GB | ✅ 모두 같음 |
| Spark (Docker, `local[8]`, 드라이버 6GB) | 압축 푼 CSV | 105.5초 / 130.4초 | 8.2~8.4GB (컨테이너) | ✅ 모두 같음 |

- DuckDB · Spark는 먼저 zip을 CSV로 푼다 — **12.0초**(한 번, 두 엔진이 같은 파일을 읽음). 처음부터 끝까지로 보면 DuckDB 약 24초.
- 빠른 추출의 1분 차이는 2024-03-15 09:00 — 4-1에서 찾은 덩어리 경계 버그와 같은 곳이다
  ([기록](findings/2026-10-21-qflow216-check-minute-chunk-boundary.md)). 이번에 세 번째 엔진(DuckDB)으로도 다시 확인됐다.
- 걸린 시간은 엔진 프로세스 안에서 잰 값이다. 파이썬 · 컨테이너를 띄우는 시간까지 넣은 명령 한 번의 시간은 0.3초(호스트) · 약 2초(Spark) 더 길다.
- 환경: Windows 11, 6코어 12스레드, RAM 32GB. 원자료는 `<lake>/_reports/bench/BTCUSDT-2024-03.json`, 실행 기록 `bench.agg_trades`(약 10분).

## 어떻게 읽나

**1. 이 크기(한 달 · 4.4GB)에서는 DuckDB가 가장 빠르다** — 정답지보다 약 11배, Spark보다 약 9~11배.
한 컴퓨터 안에서 열 단위로 벡터 처리를 하고, 엔진이 같은 프로세스 안에 있어 오가는 비용이 없다.

**2. Spark가 느린 이유 (이 환경에서)**
- 자바 가상 머신 · 작업 계획 · 셔플(데이터를 칸별로 다시 나누기) 같은 분산 처리 준비 비용이 크다. 기계 여러 대로 나눌 일이 아니면 그 비용만 남는다.
- Docker가 Windows 폴더(`/lake`)를 연결해 읽는데, 이 경로는 리눅스 안 디스크보다 느리다. DuckDB는 Windows에서 직접 읽는다 — **같은 조건이 아니다**. 이 차이가 몇 초인지는 **확인 필요**.
- 1판과 2판 차이(105초 → 130초)도 Docker 쪽 파일 읽기 · 메모리 상태 차이로 보이나 **확인 필요**.

**3. 메모리는 정반대다** — 연구 전수 추출은 한 줄씩 흘려 읽어 30MiB면 되지만 134초가 걸린다. DuckDB는 4.4GB를 쓰고 12초다.
컴퓨터 한 대의 메모리 안에 들어가는 한 DuckDB 쪽이 낫고, 메모리보다 훨씬 큰 일을 한 번에 해야 하면 흘려 읽기나 분산 처리가 필요하다.

**4. Spark 메모리 숫자에 대한 주의** — 컨테이너 전체(cgroup `memory.peak`)라 Spark 자바 프로세스 외에 컨테이너가 읽은 파일의 페이지 캐시도 들어간다.
순수 계산 메모리보다 크게 나온 값이다.

## 그래서 무엇을 정했나 · 앞으로

| 쓰임 | 엔진 | 이유 |
|---|---|---|
| Silver · Gold 표 **쓰기** | Spark + Delta (그대로) | Delta 트랜잭션 · 달 단위 바꿔 끼우기(`replaceWhere`) · 파티션 쓰기가 검증돼 있다. 기간을 늘리면(수십 개월) 메모리보다 큰 일이 된다 |
| 표 **읽기 · 검산 · 분석** | DuckDB | 같은 답을 10배 빠르게. 4-2의 교차 검산도 DuckDB |
| (검토 후보) 한 달 단위 Silver를 DuckDB로 | 확인 필요 | 이 결과로는 충분히 빠르다. 다만 DuckDB의 Delta 쓰기 지원 범위 · 달 단위 바꿔 끼우기를 같은 수준으로 할 수 있는지 **확인 필요** |
