# 0009 — 스트림: 원문 토픽에 받은 그대로, 확정된 분만 MERGE, 배치와 같은 집계 함수

- 상태: 채택 · 2026-10-24
- 관련: [스트림 기록](../STREAM.md) · [`mdp.stream`](../../src/mdp/stream)

## 맥락

실시간 봉이 필요하다. 그런데 스트림은 끊기고 · 중복되고 · 늦게 온다. '실시간으로 만들었다'보다 '배치와 같은 답을
내는가', 그리고 '틀렸을 때 고칠 수 있는가'가 중요하다.

## 결정

1. **원문 토픽 = 스트림의 Bronze**: 받은 글자를 고치지 않고 Kafka 토픽에 쌓는다(파티션 1 · 보관 7일). 처리 규칙을
   바꾸면 오프셋을 처음으로 돌려 같은 원문으로 다시 만든다.
2. **Spark Structured Streaming**: 워터마크로 '이 분은 끝났다'를 정하고, (종목, 묶음 번호, 체결 시각)으로 중복을
   거르고, 상태는 RocksDB에 둔다.
3. **배치 Gold와 같은 집계 함수**(`bar_aggregations`)로 봉을 만든다 — 두 봉이 다르면 원인은 입력에 있다.
4. **확정된 분만 쓴다**(append) — 체결이 더 올 수 있는 분은 쓰지 않는다.
5. 묶음마다 Delta **MERGE**(같은 분 덮어쓰기) — Spark가 실패 뒤 같은 묶음을 다시 써도 결과가 같다(정확히 한 번 효과).
6. 재생 원천은 Bronze 체결을 실시간과 같은 모양으로 — 키 · 장 시간 없이 같은 코드를 시험한다. 결함(중복 · 지연 ·
   빈 곳)을 정해진 자리에 섞을 수 있다.

## 다른 안

| 안 | 버린 이유 |
|---|---|
| 받는 쪽이 바로 봉을 만들어 원문은 버림 | 처리 규칙을 바꾸면 고칠 원문이 없다 |
| 직접 짠 파이썬 소비자 | 워터마크 · 상태 · 정확히 한 번을 직접 만들어야 한다. 배치와 같은 집계 함수를 쓸 수 없다 |
| 분이 끝나기 전에도 봉을 쓰고 계속 고침(update 모드) | 읽는 쪽이 아직 바뀔 봉을 보게 되고, 대사가 흔들린다 |
| append로 Delta에 바로 쓰기 | 실패 뒤 다시 쓰면 같은 분이 두 줄이 될 수 있다 |

## 치르는 값

- 봉 확정이 '분 끝 + 워터마크 + 묶음 간격'만큼 늦다(실시간 시험에서 200초 받은 뒤 마지막 2분은
  미확정으로 남았다).
- **늦음 판정은 바로 앞 묶음의 워터마크로** 한다(상태 연산자가 둘이라) — 실제로 기다려 주는 시간은 '워터마크 +
  묶음 하나'다. 재생을 최대 속도로 하면 묶음이 수십 분 치라 이 차이가 커진다(시험을 만들다 확인).
- 작은 묶음에서는 묶음마다 MERGE · 체크포인트 비용이 커서 느리다(하루 묶음 74개에 12 ~ 18분).

## 근거

- 중복 1,441 · 5초 지연 1,425를 섞은 하루 재생: 스트림 봉 = 배치 봉 **1,440분 모두, 칸마다**.
- 10분 지연 · 워터마크 1분: 65건이 버려져 26분이 달라졌고, 봉의 `ids_contiguous`가 **정확히 그 26분만** 표시.
  같은 원문을 워터마크 15분으로 다시 읽자 1,440분 모두 같음.
