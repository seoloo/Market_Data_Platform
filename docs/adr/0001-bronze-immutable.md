# 0001 — Bronze는 받은 그대로, Silver · Gold는 언제든 다시 만든다

- 상태: 채택 · 2026-10-21
- 관련: [재처리 기록](../REPROCESSING.md) · [Silver 기록](../SILVER_AGG_TRADES.md)

## 맥락

기존 연구 스크립트는 체결 원본(약 86GB)을 집계한 뒤 지웠다. 그래서 감사 규칙을 바꾸려면 처음부터 다시 받아야
했고, 받은 파일이 바이낸스가 올린 것과 같은지 나중에 확인할 방법도 없었다.

## 결정

- **Bronze**: 원천 zip을 원천 경로 그대로 보관한다. 덮어쓰지 않고 지우지 않는다. 받을 때 바이낸스의 `.CHECKSUM`과
  대조하고, 읽기 직전(Silver · 재생)에 SHA-256을 다시 대조한다.
- **Silver · Gold**: Bronze에서만 만든다. 같은 명령을 다시 돌리면 같은 결과가 나와야 한다(멱등).
- 줄마다 계보(lineage)를 남긴다: Silver 줄은 원천 파일 · `run_id`, Gold 줄은 `silver_version` · `run_id`.

## 다른 안

| 안 | 버린 이유 |
|---|---|
| 받은 뒤 바로 Parquet으로 바꾸고 zip 삭제 | 변환 규칙이 틀렸을 때 원본으로 돌아갈 수 없다. 원천과 같은 파일인지도 증명할 수 없다 |
| 연구처럼 집계 값만 남기기 | 규칙을 바꿀 때마다 다시 받아야 한다 |

## 치르는 값

- 디스크: 한 달 체결 zip 847MB. 기간을 늘리면 커진다 → Bronze는 F: 하드디스크에, Silver · Gold는 C: SSD에
  (`MDP_BRONZE_ROOT`).
- 읽을 때마다 SHA-256을 다시 계산한다(847MB 월 파일에 6.6초 — F: 하드디스크, 2026-10-24 한 번 잼).

## 근거

- 재처리 시연(4-5): 의심일 기준을 0.5% → 0.0001%로 바꿔 같은 Bronze로 다시 만들자, 7개 표 중 날 감사 10행의
  `suspect`만 바뀌었다. `RESTORE` 뒤 7개 표 모두 원래와 같았다.
- Airflow로 같은 달을 다시 만들었을 때(4-6) 7개 표가 이전 버전과 행 단위로 같았다(Silver 66,512,993행 포함).
